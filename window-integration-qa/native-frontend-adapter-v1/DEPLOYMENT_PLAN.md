# Candidate deployment plan

No main entry, legacy control socket, running shell, main profile, installed plugin or system service is modified by this staging packet.

1. Root reviews the complete frozen candidate, config builder, source/model/transport evidence and the exact fresh native campaign command. Family V8 is the accepted V21/V12 backend baseline; its direct-service call is not a completed taskbar frontend proof.
2. In an owned private HOME, copy the production payload unchanged. `install_entry` requires the exact copied legacy SHA before replacing that private copy with the reviewed native candidate. Configure existing actual V12 API owner/socket and captured shell/harness request roots through `create_config`; set the explicit route before gated shell exec. Configs are not rewritten during requests.
3. Run the genuine taskbar preview/minimize/restore campaign with actual held input/release and native outcome observations. Keep every refusal/uncertain outcome and prove no duplicated send, fallback, unexpected helper, actor leak or main change.
4. Before a production proposal, implement and formally specify the rest of the public `hypr-windowctl` CLI operations that this candidate currently refuses: focus/close/center/maximize/snap and other supported actions. Review desktop ownership/config persistence, active session handover, versioned source/loader packaging, API lifecycle startup/shutdown, journal recovery and route/error policy. The limited minimize/restore candidate is not a drop-in complete product replacement.
5. Prepare a concrete installation/activation and rollback artifact for review. Preserve the legacy installed entry and config bytes with exact versioned paths; explicitly route the new complete frontend to a running verified V12 instance. Reload shell only through the reviewed public plugin reload mechanism. Production activation remains a separate user-authorized root action after the real integration and public CLI compatibility gates pass.
