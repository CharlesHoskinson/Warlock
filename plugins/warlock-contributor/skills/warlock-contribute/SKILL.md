---
name: warlock-contribute
description: Implement or repair Warlock Elm/native GUI code in the original scenario delivery loop, with source ownership, proportional verification and evidence-scoped reporting. Use for Warlock code contributions; unrelated repository work does not need a product slice.
---

Deliver a runnable user behavior in `implementation/warlock/`. Read repository `AGENTS.md` and `docs/warlock-build-loop/v2/INSTRUCTIONS.md`; these remain authoritative after compaction. Read the October 7 AAR once when entering this workflow. Do not turn contribution records or plugin passes into product completion.

For a new checkout, `doctor` reports local package/CLI availability without launching clients or installing anything. Use `plan` to scaffold a slice with exact original scenarios, actual source paths and decisive verification; save its `--json` output in ignored scratch and pass it to `start --slice-file`. After compaction or a contributor handoff, use `handoff` to see changed sources, protected foreign drafts, stale observations and remaining evidence before resuming. See [scaffold and resume](../../README.md#scaffold-and-resume) for commands. These helpers do not select work or change ownership, the ledger or acceptance.

For plugin development or checkout troubleshooting, `doctor` also validates local package metadata and references. `self-test` runs only the plugin regression suite with temporary Git fixtures, reports failures and refuses an empty suite. Read the test code before running it. These are support checks, not an extra prerequisite for every GUI slice or evidence of client trust/native acceptance.

Handwritten surface adapters are production source; compiled Elm JavaScript bundles are artifacts. `verify-plan` includes the known adapters and CSS in the relevant view route, while preview transports remain explicit unmapped source requiring a chosen proportional check. Recording changed adapter bytes observes implementation work, not a delivered GUI feature.

Use optional `preflight --slice-file <saved-plan>` to preview source conflicts and record availability before `start`. It writes no files and adopts no drafts; selected dirty files still require an actual ownership decision. Existing records should be resumed with `handoff` or retained while choosing a new global `--record`. Saved plan packets must retain exact selected originals; `start` rechecks them and current dirty files. See [scaffold and resume](../../README.md#scaffold-and-resume).

Use `remaining --requirement <original-ID> --markdown --limit 3` for a bounded feature checklist or `remaining --summary` for recorded scenario counts. Follow the reported offset with the same filters and compare ledger hashes before combining pages. It copies original oracles and recorded missing observations; it does not verify acceptance or equate unadjudicated with absent implementation. The full release has obligations beyond this baseline.

If the original IDs are unfamiliar, `capabilities` lists their exact capability groups and IDs. Use `remaining --capability <exact-name> --markdown --limit 3` to narrow the backlog, then `inspect --requirement <ID> --scenario <exact-name>` for the selected scenario and its ledger row. Narrowed inspection retains the requirement statement and verification obligations, with explicit omitted-scenario counts. These commands select no work and change no records. See [scaffold and resume](../../README.md#scaffold-and-resume).

Find the repository root and prefer its `plugins/warlock-contributor/scripts/warlock.py`; pass explicit `--repo <root>`. If that file is absent, restore the repository package before product work. Installed hooks locate their checker two directories above this skill. A cached checker that differs from the repository checker refuses to certify it; refresh the installed package and inspect the current skill before using its hooks. Run `python3 -B <plugin>/scripts/warlock.py --repo <root> status`, inspect the active slice and dirty source paths, use `inspect --requirement <original-ID>` for exact EARS/ledger/OpenSpec pointers, then `check --project-only` for initial inspection. Before `start`, confirm Git ignores the default scratch directory `.warlock-contributor/`; on a new checkout add that narrow ignore or select an already-ignored location with global `--record`. Commands are offline and do not run QA. A nonzero check means inspect and fix structural findings before making the contribution claim; session hooks are advisory reminders and cannot replace explicit calls.

Before implementing, select one slice with 1–3 original EARS IDs and exact original scenario names. Read their objects in `docs/elm-roadmap/requirements.json` and the matching `openspec/changes/elm-desktop-pivot/specs/` capability. Read only relevant architecture, Warlock philosophy/design-language and FRP adoption constraints. Preserve original scenario oracles and deadlines. Update the active slice through the repository workflow, then run `start --owner <accountable-owner>` and `check`. Resumed own drafts require explicit `--adopt-dirty <declared-path>` and `--ownership-note`; do not adopt another contributor’s work. Use `start --slice-file <repo-relative-json>` only for an explicit alternate slice; inspect CLI help and [the contribution contract](../../references/contract.json) before supplying custom records.

Make the slice concrete: state what the user does, current failure and intended visible result; name actual source entry points, ownership, and the decisive behavioral observation. Inspect candidate ancestry and existing modules before extending the real Elm model/update/view and narrow native bridge. Integrate into the runnable root rather than creating another versioned prototype. Elm owns ordinary policy; native effect authority validates current grants/incarnations/revisions. Unknown outcomes require reconciliation without replaying mutations. Preserve other contributors' changes; supporting infrastructure must identify an observed blocker and original scenario it unblocks.

If the same behavior needs another source dependency, use `extend --path <candidate-relative-file> --reason <concrete-dependency>` before editing. It preserves the slice's IDs, history and progress timer instead of starting over. Dirty dependencies require exact `--adopt-dirty` paths and an ownership note; changed protected drafts cannot be adopted to hide an overwrite. Previous claims become historical for the expanded tuple, and fresh claims must identify every source. See [scaffold and resume](../../README.md#scaffold-and-resume). A different behavior needs a deliberately selected new slice; declarations alone are not progress.

When locating code, use the [implementation map](../../references/implementation.md) for the relevant shell, view, catalog, pins, outcome or native-surface responsibility. Inspect its actual integration route before extending it; component replay remains separate from native delivery.

Use `verify-plan` for protected check suggestions based on declared sources changed since the last record; `--selected` plans before edits. Inspect each runner and its prerequisites, choose the decisive behavior and negative/lifecycle observation, and handle explicit unmapped/support paths yourself. It executes nothing, and suggested native modes do not cover every original oracle. No source changes means no default rerun. See [proportional verification](../../README.md#choose-proportional-verification).

The required checks expose a structured `progress` packet with the recorded elapsed time, nonprogress iteration count and slice-change action. Honor its two-iteration/45-minute investigation trigger while continuing independent mandatory work. These fields describe self-attested records; they cannot establish delivered GUI behavior.

Compile changed entry points/units and relink through the protected QA launcher. Run a decisive behavioral regression and meaningful negative/lifecycle case when behavior changes. Add Quint/fuzz for changed concurrency/authority/reducer invariants; broaden regression only for a concrete dependency, failure or integration milestone. A prose correction or independent view change does not require a universal full-suite/model/review gate. Follow [the protected execution commands](../../references/workflow.md); do not run GUI runners or raw compilers outside the required launcher, restart the main compositor, or invent a new activation approval gate.

Use `claim` when preparing an observation: it copies the exact selected oracle and verification obligations, hashes existing evidence and all declared sources, and prints a `claimSchema=1` packet for `record --claim-file`. Supply actual scope, disposition and missing observations; it uses the participant owner as observer and cannot scaffold acceptance. It does not write records or judge evidence contents. See [the claim example](../../README.md#scaffold-and-resume); read the referenced reports yourself.

Record actual results with `record --outcome production-fix|scenario-verdict|qualification --summary <observed-result>`, followed by `check`. This record tracks the slice; update original scenario rows separately when evidence warrants it. Read the contract before using `--claim-file`. Match physical/native/keyboard/AT/IME/hardware claims to original evidence obligations; bridge evidence applies only where the original permits it. Hashes and checker compliance attest to structure and custody, never to oracle truth. Keep unavailable observations explicit and full release acceptance separate. After two qualification-only iterations or 45 minutes without a production fix/original verdict, end that investigation and pick another mandatory product slice without bypassing safety.

Report the visible behavior and original IDs advanced, observed failures, remaining native/AT evidence, and next source change. Re-run the checker before final reporting. Respect existing commit/publication authorization and preserve failed reports; do not count commits, checks or administrative records as GUI features.

Use `report --markdown` to prepare a delivery note from the record, or global `--json` for automation. It retains intended versus observed results, original obligations, evidence scope and uncommitted paths. Read the evidence and review the note before publishing; stale observations return nonzero and must stay explicit. This helper does not post anything or infer acceptance. See [delivery notes](../../README.md#prepare-a-delivery-note).

When preparing a commit, `review` checks the staged contribution against declared sources and recorded evidence and compares staged bytes with the working copy. Explicitly include owned supporting files with `--include`; foreign drafts remain protected. See [contribution review](../../README.md#review-a-contribution). This helper is optional for unstaged work and performs no publication or QA; its pass does not replace the original scenario observations.
