# Constraint sketch review

V156 is types only, with approval pending. Preserve it and its typecheck as the original proposal. This review adds no model functions, actions or invariants. Typechecking does not establish coordinate correctness or native acceptance.

Before logic, represent these distinctions explicitly:

1. **Bound coordinate spaces.** Current Constraints.client/layout values are already normalized to one target-size space. That removes the faulty-conversion behavior the future model needs to detect. Keep raw configured-client/protocol bounds and layout/rule bounds tagged separately, together with a validated or unavailable coordinate conversion observation. Preserve positive raw maxima hidden by core normalization and legitimate rule absence.
2. **Prospective operation geometry.** Transaction.desired is one Rect. Replace or supplement it with a prospective record containing logical target rectangle, visual target rectangle, real window rectangle, and actual configured-client Size. MAX chooses a rounded workarea/visual target and subtracts reserved compositor decorations. Ordinary floating restore sets its saved logical box directly. A shared normalized-client rectangle cannot stand in for both operation paths.
3. **Coordinate dependency.** Add a coordinate observation/revision covering current xdg window-geometry origin, reserved decoration extents, relevant rounding semantics and conversion availability. Store the operation’s captured observation in its dependency/before state. Output scale should remain separate from logical configure dimensions; do not encode a fake Wayland scale multiplication. Abstract integers deliberately, with fractional native measurements/rounding qualified outside the model.
4. **Absent versus unknown.** MissingBounds currently maps every missing observation to refusal. Absence of an optional window rule or an unbounded maximum is a valid native observation, whereas unavailable/untrustworthy data is a refusal. Distinguish absence/unbounded/known bounds from unavailable/invalid conversion. Both axes may have independent unbounded maxima.
5. **Retained original context.** Exact restore feasibility requires the saved logical/visual placement and the current operation-specific conversion, not merely testing both saved rectangles against a single interval. Coordinate changes can preserve or invalidate exact restoration; never substitute a clamped original. Current workspace/output fields omit workspace ownership generation and distinct output ownership generation. Carry the inherited full placement scope or explicitly mark it as an external validated opaque prerequisite; numeric ID alone cannot prove owner identity.

Keep separate request/client/presentation observations and preserve the existing full native binding/protocol/intent journal outside this focused model. If protocol2 remains a fixed abstraction, say so rather than implying cross-protocol correlation is modeled by RequestKey. Keep baseEligible as an explicitly inherited native-policy abstraction; it does not prove all lock/family/nonfloating guards.

Revise SPEC’s normalization paragraph to require a validated, operation-specific relationship between spaces before intersecting bounds. Each constraint source must be checked against the corresponding prospective dimension, or transformed through the audited conversion; do not compare raw hint dimensions directly to workarea/visual sizes. The intended common-space normalization may be a successful result of that conversion, not an assumed input.

A fresh type-only proposal can include tagged bound observations, CoordinateObservation, ProspectiveGeometry and complete PlacementScope records; it should be typechecked and presented for explicit approval before logic. Named later witnesses should distinguish feasible GTK lower bounds from infeasible MAX; zero/unbounded vs positive tiny raw maxima; nonzero/negative geometry origin; compositor decoration reservation; operation-specific MAX/restore dimensions; stale coordinate revision; and legitimate absent rule versus unavailable conversion. Original V156 remains pending and unchanged.
