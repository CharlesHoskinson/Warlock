## Versioned amendment to the accepted-read contract

A requested read is an expectation for a future reply. It does not invalidate a
previously accepted post-proof observation. Each slot retains the last actually
accepted action read ID/context and geometry read ID/context independently until
another reply in that domain passes the existing public Shell reducer. Issuing a
new request only changes the matching expectation for that future reply.

An accepted reply may immediately drain dirty notifications and start another
batch. The resulting Reconciling UI phase is not evidence that the just accepted
reply failed. Acceptance relies on the before/after admitted request correlation
and actual accepted observation, not the resulting UI phase.

A release builds601 Expected from the last accepted post-proof pair. Outstanding
next request IDs do not reject an exact qualified release for that completed pair.
A subsequently accepted reply replaces its domain stamp, so an obsolete release
must then refuse. New native user intentions remain gated by existing Shell
availability while next reads are pending. No intent is sent by observation,
acknowledgement or release.

The original v611 `retry-pending-invalidates-prior-read-qualification` assertion
is preserved in that immutable packet. The explicit replacement assertion here
is `pending-retry-retains-completed-accepted-pair`; no old test is silently relabeled.
Both final-reply orders have public compiled witnesses: accept action, queue dirty
notification, accept geometry and drain; or accept geometry, queue dirty, accept
action and drain. The original pair releases the old live reservation, preserves
Unknown history/counters and emits no mutation. Identical-input original611
compiled differential witnesses remain blocked in both orders.
