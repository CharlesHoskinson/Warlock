# Native lost-release preparation v641

This packet prepares an additive campaign and does not launch native QA. It is
separate from the original 135-window journey and preserves its six-second wait
and real pointer functions byte-for-byte at AST level. The target must be a fresh
reviewed GUI that fixes the confirmed v630 repeated-reconnect liveness defect;
this preparation does not certify v630 or an unbuilt v640 tuple.

The runner uses the actual frozen daemon input from the selected full GUI build,
the qualified594 native authority/core pair and real GTK fixture. Its external QA
wrapper changes only daemon.send. It forwards every frame until the first actual
host-reservation-released. That frame must match a persisted current delivery
certificate, whose digest and exact original Released Unknown archive anchor are
verified by read-only private-file inspection. The wrapper never creates an
authority request, proof, native read, effect, ledger entry or frontend frame.

Before suppressing that frame, the wrapper writes a campaign-bound 0600 single-link
marker using O_EXCL, loops over partial writes, fsyncs the marker file and its
private 0700 directory. It raises the actual daemon OutputFailure before wire
publication and poisons the actual output writer to prevent a further diagnostic
frame on that lane. A later backend startup validates the consumed marker and
forwards frames normally. Unsafe, malformed or partial markers fail closed; they
are not silently deleted or rearmed.

The native journey starts an actual Pending user intent while its broker is
stopped, verifies that the effect was not optimistically applied, then kills that
broker. The same Elm webview survives and retains Unknown. The first explicit user
Reconnect obtains real retirement proof/current reads; the wrapper deliberately
loses the resulting release after certificate persistence. The second explicit
Reconnect must use a fresh binding, reannounce exact historical Unknown and
persist a new delivery certificate that clears the retained UI reservation.

Acceptance compares exact immutable original history, fresh certificate anchor,
strict wire trio, original Unknown transaction, unchanged effect journal and
allocation watermarks, single-use marker and same webview PID. Old binding replay
must be refused. Only a new real user action may submit the next request/generation
and apply minimize. These are proposed executable oracles, not observations until
root runs the reviewed campaign against the coherent target.

CPU controls compile the copied actual624 C admission producer, create real V6
and sidecar certificates and exercise suppression, marker privacy/restart,
unmatched certificate/current binding, unsafe markers and marker I/O failures.
Those CPU proofs use synthetic constructable retirement/read inputs and claim no
native authentication. The runner itself uses no synthetic native response.

The preflight generator requires an explicit GUI directory, separate output JSON
and a new native evidence directory. It verifies built source/binary/assets,
native ABI pair and held authority dependencies, plus the unchanged pointer/wait
AST. Root selects and reviews the corrected target, prepares preflight through
the protected CPU launcher and alone launches runner through the serialized
native build-loop wrapper. No installed configuration or primary ledger is used.
