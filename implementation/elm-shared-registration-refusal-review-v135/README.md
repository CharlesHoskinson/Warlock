# Registration refusal review

This lane copies unchanged production modules from the frozen V132 component. Its QA worker calls the actual reducer and `OutputController.register` just as Main does. Synthetic observation replies establish a ready controller; no native process or operation runs. The worker exposes attempted effects separately from the registered packet. Two isolated tests repeat a real reducer effect 17 times or append a large Unicode focus field to stress the registration boundary; these do not claim ordinary UI reachability of those packet sizes.

The compiled reproduction finds a usability failure. After allocating an operation, registration can return `Nothing` because the 16-record inventory is full. No packet is published, but both effect protocols retain the exact issued mapping and unresolved Pending transaction. Observation allocation similarly retains expected IDs for requests never forwarded. Ordinary notifications do not replace those reads. Missing presentation scope also suppresses the initial observation while retaining its expected ID. The batch exhaustion bit remains latched; even a matched admitted certificate releasing one earlier record does not restore transport or discharge the dropped reads.

Menu selection has a narrower distinction: stage1 reserves a local Menu intent and allocates paired observations. Registration refusal blocks those observations; the existing preparation deadline cancels the local Menu reservation without inventing a native operation. Its remaining transport exhaustion/read state still needs explicit recovery. A native Pending mapping is never allocated by that stage1 test.

Main commits the returned packet only when it is `Just`; its timer list does not implement an operation/read registration rollback. These commands are known locally not to have been submitted, unlike a possibly submitted native command awaiting its original receipt. Native preflight certificates cannot resolve a rejected packet because there is no registered batch or native delivery for it. V122's certificate-only exact local terminal therefore cannot be invoked through the normal certificate route for this case.

The characterization suite records these actual states as successful reproductions. A separate protected usability report applies three required assertions to those compiled outputs and fails: neither protocol may keep an indefinitely Pending issued mapping after proven local non-submission, and dropped observations may not keep expected IDs indefinitely. These failures are retained; no fix is implemented and usability/native acceptance is false.

A subsequent implementation should make registration's result typed: submitted, presentation-only, or local non-submission with the original complete keys and a bounded reason. Only the specific attempted operations proven unsent may receive a dedicated local terminal through Shell and the original Menu router. Existing unrelated Pending/Unknown and original receipt keys must survive. Matching observation IDs should be retired without immediately trying to reissue into the same blocked registry. Expose transport refusal and define explicit bounded recovery before permitting another action. Capacity release, terminal overflow, and authoritative scope replacement require separate recovery policies; never evict unresolved batch records or replay an operation to solve this. This is local proof, not a native receipt or certificate. V132 and frozen V122 remain unchanged.
