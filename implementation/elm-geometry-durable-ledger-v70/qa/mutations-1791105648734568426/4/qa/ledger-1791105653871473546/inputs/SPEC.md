# Durable unresolved-operation ledger prototype

This plain-language contract extends the reviewed primary V275 singleton journal without changing it. The primary checkpoint was V279 at 2026-10-04T09:04:50.456379Z. Later primary work must be merged explicitly. No new Quint logic or native/host integration is included.

* The native compositor lifetime selects the existing verified private namespace. Original full binding, effectProtocol and complete intent identify each entry. Protocol1 accepts minimize/restore/activate; protocol2 accepts maximize/restore-geometry. Observed legacy/geometry revision meanings remain independent.
* A new begin persists Pending before the caller may submit once. Its return True permits that newly admitted submission; exact duplicate returns False and permits no submission. Any different key targeting the same native incarnation is blocked across operations, protocols, session/frontend changes while unresolved.
* Up to64 unresolved targets survive independent operations and process restarts. No eviction. The 65th begin fails without altering bytes. Definitive exact original receipt removes exactly one entry; Unknown retains it. A receipt with changed binding, version, intent/context or target cannot settle anything. Terminal duplicate receipts fail without changing bytes.
* Shared request/generation high-water marks across both protocols persist per original full binding. Reusing or regressing either counter fails. Up to128 allocation scopes are retained; a new129th scope fails closed. This metadata budget is explicit and is a further production recovery/availability design gate, not an unbounded promise.
* One atomic schema3 collection is bounded to512KiB. Its entries are normalized schema2 records; the prior strict legacy records remain readable through unchanged inherited primitives. Bootstrap imports existing host and broker singleton evidence under both writer locks. Exact settled broker evidence supersedes the same admitted key; other unresolved keys survive. Contradictory unresolved same-target evidence fails rather than guessing.
* Both inherited migration and new storage use private/no-follow descriptors, 0600 single-link records, nonblocking writer ownership and bounded reads. A ledger snapshot keeps source hashes of old singleton evidence. Any later old producer modification fails closed: this prototype requires quiescing the old producers and does not silently ignore their new admissions. Production host per-key admission and old-live-broker revocation remain separate integration gates.
* Writes retry EINTR and partial progress; zero progress fails. File fsync precedes atomic rename; directory fsync follows. Failure poisons the current Ledger object so no further mutation or recovery response is allowed without explicit close, storage correction and reopening. No automatic retry or effect replay occurs. A directory-fsync failure after rename may leave the new complete bytes visible; it still reports failure and cannot authorize submission or receipt delivery. No claim of durable success is made from that failed call.
* `recover(current_binding)` returns internal informational records with each original binding/key and status Unknown plus allocation watermarks. It emits no native request, receipt, broker wire frame, observed scene or geometry. Its binding argument must have the same native lifetime. The future Elm integration must merge these entries/allocator maxima and await fresh independent observations.

API: `Ledger(runtime,instance,lifetime)` context manager; `begin(binding,intent,effectProtocol=1)->bool`; `settle(exactNativeOutcome)->None`; `snapshot()->validated deep copy`; `blocked(lifetime,incarnation)->bool`; `recover(current_binding)->informational DTO`. Callers must respect False and every exception. There is no public raw mutation, automatic native operation, or persistent executable retry queue.
