## Why existing code cannot simply be reused unchanged

`qa/check-attention-current.py:18-26` already accepts explicit build receipt+SHA; it validates successful root-set and hashes then independently checks current Elm set at end. `qa/check-shortcut-draft.py:31-34` accepts the same pair, but candidate coverage does not bind build's complete source-set to current set (its final inventory check compares its newly captured sources to themselves). Shared validation removes this drift and also verifies actual output assets.

Private `shortcut-draft-build-root-v2/build.py` pins source-pins.json plus arc004-build-terra2-v1 report to obtain static assets. It compiles symlinked current src, copies entire cache, and only installs full provenance in the success update. The new recipe replaces these maintenance and failure-retention weaknesses without adjusting historical receipts.

`adapter/release_builder.py:205` captures broad source/tool/compliance/native closure; `:528` stages inputs, `:557` owns the same three roots, `:561-578` rebuilds host and compares historical host/assets, `:593` packages workspace assets. Its historical tuple equality is meaningful and must remain. `release_tuple.py:136-156` binds historical product sources and host artifacts. Removing those bindings would misrepresent a new candidate as historical reproduction. Full release and two-build distributable comparison remain separate gates.

After the new recipe is proven, a later selected refactor can make release_builder consume its shared root mapping/staging primitives while preserving every release lock role and strict nativeTupleReference check. Do not make release_builder consume an externally supplied unverified assets directory, and do not silently change its lock schema or source closure in this first slice.
