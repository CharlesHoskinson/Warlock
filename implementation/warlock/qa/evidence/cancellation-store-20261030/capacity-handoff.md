## Future terminal capacity

`_future_record_bytes(record)` computes a conservative encoded-size envelope from the actual schema for this immutable key; it does not invent or persist a native receipt. Canonical native counters are at most UInt64 max (20 ASCII digits), so unknown future preparedId/revision/outputGeneration use that maximum-width value. Binding, complete Restore intent, key and original deadline are immutable actual values and retain their exact encoded lengths. Prepared, outcome and ACK object keys are the exact strict production cancellation_endpoint schema. Terminal status/reason pairs are selected from actual Committed/applied, Cancelled/cancelled-before-commit and the production `_REFUSALS` vocabulary; the maximum actual encoded pair is used. Unknown and prepared are also considered for lastObserved. This includes all future native reason strings allowed by the strict client, not representative samples.

The upper record includes prepared + lastObserved + certificate.response + full ACK simultaneously; certificate digest width derives from SHA256.digest_size*2. Maximum encoded V7 stage/ack enum values, all three unique attemptedKinds and maximum lastOperation are included. The size-only boolean is false because its JSON literal is longer than true. Optional nulls are smaller than the populated fields selected here. These maxima are deliberately a size envelope rather than a valid native/effect state and are never serialized to storage or sent as evidence.

Proof of headroom: for record r, define M(r) as this maximum encoded length and L(r) as actual encoded length. The required envelope size is actual envelope length + sum(max(0,M(r)-L(r))) over EVERY retained record. Replacing a record by any schema-valid future version under the same immutable key/deadline cannot exceed M; object/array separators and all other envelope bytes remain in the actual envelope term. Record growth consumes its reserved difference rather than new unreserved space. Existing per-write immutability/monotone guards prevent changing those inputs. `_validate_v7_locked` applies this calculation on every read/write, and cancellation_reserve explicitly refuses under host_guard before the durable write/submit permission if it would exceed one MiB. Therefore an unrelated legacy write must also preserve all outstanding records' headroom; checking only the initial reservation would have been insufficient.

No optimistic constant or sampled maximum is used. The 64-record limit and all existing legacy bounds remain. Credit is conservatively retained for historical records rather than opportunistically reclaimed. Existing pre-patch state that overcommitted future capacity fails closed on reopen; the patch does not drop history or manufacture room. An external host may still write an admission that cannot be imported within the remaining envelope; that remains blocked/unsubmitted, not permission to steal reserved capacity. Actual ENOSPC/fsync failures remain storage-fault cases and are not prevented by a logical byte bound.

## Informational recovery

`cancellation_recovery_frames(bound)` now validates and snapshots nonempty history under one host_guard and returns one explicit `host-cancellation-recovery` protocol1 DTO per record. RECOVERY-PROTOCOL.md defines its exact fields. All uncertified history reports Unknown; known terminals retain their entire original certificate nested in the original record. Current outer delivery binding never replaces original inner ownership, and executionAuthorized is always false. The method performs no native action, ACK, replay, attachment or admission retirement. Existing coordinator startup calls this API already. Root must separately wire and qualify the currently absent C/Elm consumer; this is not end-to-end historical-certificate delivery.
