The daemon proposes one explicit configuration boolean, `cancellationOptIn`; omitted/false uses the existing `Journal(runtime,instance,lifetime)` call and existing unsupported-request fallthrough, with no coordinator import. True alone selects `Journal(...,cancellation=True)`. This name is a **private proposed configuration**, not an approved public interface; no frontend timestamp or C/Elm route is introduced. A non-boolean is refused. The actual daemon calls its selected `Endpoint.hello()` first; only then does it construct `CancellationCoordinator(client,recovery,hello)`, compare the strict hello kind/version/full binding to the currently authenticated client, and call the actual `cancellation_attach(bound)`. No frontend frame or recovered record creates attachment. The coordinator is registered with the same `ExitStack` after the store, so its `close`/detach runs before store close on normal EOF, connection failure, output failure and other exits. On observed lost or changed client binding and strict-client lifecycle exceptions it detaches, clears only the coordinator's ephemeral handles/ACK cache, and refuses further use. Detach failure poisons/closes the coordinator and propagates; it does not erase journal records. A failed/double attach is never followed by blind detach of someone else's grant.

The store's `cancellation_attach` clears `_live_cancellation_keys`; `cancellation_reserve` adds a key only for a newly created record in the current attachment, while exact existing records return `submitPrepare=False`. V4 additionally requires its own live-owned handle before returning a duplicate prepare observation, including terminal status. `_record` requires the exact current binding, full intent/deadline/preparedId and an actual in-process strict-client handle. Therefore snapshots, old reports, same-binding reopen and native query cannot reactivate an old key. Startup's snapshot/locally certified finish and `cancellation_recovery_frames` remain informational, with the original stored binding and `executionAuthorized=False`; no native prepare, commit, cancel, query or ACK is sent at startup.

V3 ordering remains: store reserve and atomically attempted operation (including monotone `commitAttempted`/`attemptedKinds`) precede strict native transport; the typed `_native_cancellation_evidence` factory is used only after an actual strict client call; terminal observe persists the complete certificate, finish performs exact Pending removal and directory barriers, ACK-pending persists, then native ACK and acknowledged persistence precede return. Unknown never ACKs, no Cancelled-to-Refused conversion or default fallback exists, and duplicate commit after Unknown/query-Prepared cannot call native again. Store methods are invoked before/after network calls and their own `host_guard` returns before transport; the coordinator's threading lock is not a filesystem lock. Actual store's `cancellation_reserve` also checks workspace marker/journal and exact legacy Pending under its own host_guard; its tests and implementation must remain unchanged by this proposal.

Inherited ACK protocol caveat: current proposal automatically sends native ACK after durable finish and returns the terminal, and a later explicit same-grant ACK request returns its cached validated ACK. This is inherited from v3 and requires root's protocol review; no assertion that C/Elm currently speaks this route. The direct deadline field is only the frozen opt-in input to this private coordinator: no frontend is being made a clock authority and the host/C deadline contract remains a separate required stage. Existing legacy, original deadline, full owner/binding and correlation checks cannot be relaxed.
