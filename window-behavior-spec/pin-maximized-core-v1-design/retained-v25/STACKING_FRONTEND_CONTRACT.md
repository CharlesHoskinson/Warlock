# Persistent pin stacking and captured frontend before implementation

V2 remains unchanged. V24 native pin/action/lifetime semantics and accepted53named action model remain baseline. ConfigActions::alterZOrder delegates this same core primitive but also calls simulateMouseMovement; maintenance must not inject that pointer movement. Existing family hook on WindowState::raise is preserved. No installed-binary/source-equivalence claim is made from primary attribution alone.

Native pin bit plus one raise is insufficient to claim persistent always-on-top: installed pin.lua explicitly maintains it on window.active. Its address loops/fades are not reused.

## Persistent native stacking

Maintain actual live mapped normal floating pinned application owners above eligible unpinned floating applications using the public owning WindowState::raise primitive. Preserve actual pre-hook relative order of independent protected owner units, including pre-plugin live pinned windows. Visible modal/transient descendants moved by core/family raise belong to the effective protected unit without changing their own independent pin bits; existing deepest-modal raise/hit/focus policy remains authoritative. The source of order is actual public WindowState::windows stacking order (official retained efb509 WindowState.cpp: bottom front/top back, move-to-top rotates existing entry); no guessed sort by PID/address/family or creation time. No focus, pin, geometry, workspace, monitor, opacity or fullscreen writes occur in maintenance. Layers/taskbar/modal policy stay core-owned. Normal workspace/monitor transfers preserve pin intent; minimize/fullscreen/special/unmapped state excludes the owner until eligible again. Actual native focus/restore/open/pin/transfer events trigger bounded maintenance; synchronous action completion requires the resulting actual captured stacking predicate, not only successful core action ACK.

Every maintenance capture binds strong actual owners, full generation/session/incarnation/config epoch, current actual order and per-member pin/float/eligibility. Reentrant requests are coalesced; a captured pass raises each effective protected owner/unit in original bottom-to-top order, avoiding duplicate logical requests. Before each write and after callbacks, identity and current eligibility are checked. Changed epoch, owner closure/reuse, pin/floating/fullscreen/workspace eligibility or backend refusal invalidates the pass; it cannot report complete or write stale owners. Partial stacking is retained as diagnostic failure, no rollback or logical pin request retry. A fresh causal native event may request a new pass. Telemetry is bounded and distinct from completed pin action.

## Genuine frontend

Launcher Pin to taskbar retains its own existing persistence meaning. Add a per-window preview context-menu action labeled Toggle pin. Menu creation captures the actual public address/stableId/PID once and issues an owned read-only native capture query; it receives the full nine-field native token. It cannot select an active window or another group member when capture fails. Capture completion must match the same live menu generation, original public identity and private process/socket authority before enabling the action. Dismissal, replacement/new menu and stale capture reply invalidate it. The full native token is immutable until the one actual user invocation, including keyboard activation of that menu item. It is never reacquired at click time, and no previously displayed Pin/Unpin intent is invented. Toggle uses current pin state of that exact native owner at execution.

The actual QML Process executes only the root-reviewed exact isolated helper entry with toggle+captured JSON token; helper/config/env/interpreter/stdlib/loader/source bytes and requester lifetimes are pinned. Native completion must be the complete typed snapshot root helper accepts. Errors/partial/uncertain results show failure and never queue a retry. Real titlebar button invokes reserved synchronous owning command; real SUPER+P and SUPER+CTRL+T handlers capture public active owner synchronously and call pin_window once. Focus changes cannot redirect captured actions. No QA direct pin_request call counts as frontend acceptance.

## Legacy and maximized requirements

On plugin/service adoption, query actual current native live-window state without toggling it: preexisting pinned/floating/geometry/workspace/monitor/focus stay unchanged except modeled stacking precedence. Unproven old minimize records do not supply generation/session history; they cannot silently authorize restore or rewrite current pin intent. Separate migration/recovery authority is required. Current core pinWindow refuses all fullscreen modes, including maximized; V24 explicit refusal remains baseline. Do not substitute unmaximize/resize/float semantics for maximized pin support. A supported maximized policy needs exact primary core feasibility and its own formal/geometry/restore contract first; fullscreen refusal cannot stand as completed maximized parity.

## Source-stage acceptance

Formalize frontend menu generations/fulltoken and stacking capture/invalidations before new frontend/native edits. Actual private QA must use real pointer/keyboard/titlebar/menu events across live pre-plugin/pre-service/new windows, independent family members, minimize/restore, rapid ordering, focus overlaps, reload/reduced and monitor/workspace transfer. Actual core stacking/hit/focus/window lifetime/pin state and full helper reports remain authority. Source/CPU/model checks do not close native or full Windows parity. Root exclusively launches GUI/input; no main changes or freeze before complete source handoff.

The same maintenance runs after both public core raise and lower entry points. An explicit core lower may reposition a pinned owner within its protected band, but cannot leave it below an eligible unprotected window. Core lowering during an active captured pass invalidates that pass before any further owner write. Existing family raise repair remains authoritative; the new lower hook introduces no focus/input calls. This refinement is proved before installing the lower hook.
