# Per-query housekeeping transaction admission

The frozen V25/V10 baseline remains failed. Its three real captured sources were seeded, uploaded and presented; the durable retirement gate refused the retained cache housekeeping timeout. The refused exact `j/clients` row had the correct compositor peer, 3664 reply bytes and complete EOF, and lasted 1020.004093 ms from registration to final publication under the original 0.6 s budget. Its interval overlaps recorded ready and watchdog command completion timestamps. The exact native lock holder and deadline check site are unproved. Root's actual frozen CPU fixtures independently establish reservation contention as a reachable path, including an ordinary ready commit.

The fresh correction changes only scheduling at NativeFactory.housekeep. Each of its original three fixed read-only commands acquires the existing journal_lock before calling OwnedCommands.check_output. The same RLock is manager.lock and ReadonlyIPC.reservation_lock in real bind_journal assembly. Each individual query retains the lock until the unchanged read-only call returns or raises, including authority, unconnected registration, exact peer/socket/lifetime, full EOF/shape, descriptor closure, durable publication and post-publication confirmation. The lock is reentrant for those original same-thread ledger operations. The original absolute 0.6 s query deadline is created once inside the unchanged ReadonlyIPC.query after admission. No existing query deadline is reset, paused or enlarged.

A native receipt transaction may finish while housekeeping waits for admission. No socket query has started and no descriptor has been registered during this waiting phase. Once admitted, another thread cannot perform a receipt transaction until the query has returned or refused and the wrapper releases its lock. A malformed, incomplete, foreign, stale or late response remains refused; the original closed refusal ledger and housekeeping error persist. Success after a failure never erases the earlier error.

The lock is released after EACH query, rather than across the whole clients/native/clients sequence. Receipt ingress and native work may run between observations. complete_live_identities must still reject every changed or incomplete identity tuple set; prune still requires complete=True and nonblocking=True. No cache prune authority comes from admission itself. Actual three-query command order, environment, 0.6 s timeout, guard checks, last-actor cleanup and coverage assertions stay exact.

This trades potential admission waiting and transaction-length ingress blocking for exclusion of native receipt commits during an active housekeeping query. The 0.6 s network/read-only deadline is not a global bound on acquiring admission or all authority/journal IO. Healthy transaction latency must be measured with the actual CPU Unix-peer/RuntimeLease/ReadonlyIPC fixture; lock release and genuine ingress opportunities between queries must be proved. Holding the lock over all three commands could serialize up to 1.8 s of network budgets plus IO and is deliberately excluded. Existing service shutdown join8s and controller2s deadlines are unchanged; a transaction/owner that fails to finish still refuses normal shutdown. No unbounded wait is accepted as a native performance claim.

The two inherited cache fixtures allocate NativeFactory with __new__ and omit actual journal lock assembly. Add only a genuine threading.RLock to each test object. Their original query count, guard count, full live-pair assertions, incomplete-coverage refusal and untouched-cache assertion remain byte exact. No fallback to a null context is permitted for a missing lock in product code.

ReadonlyIPC, NativeSession, OwnedCommands, Keeper, receipt/context/source/native/retirement code and all baseline38/fault34 oracles remain unchanged. Repeated ready/deadline command submissions are retained as observed guard/latency work; the actual core's special-workspace no-op means duplicate native state mutation is unproved. This correction does not skip fallback or change reduction semantics. Formal/source/CPU proofs do not accept the native baseline or authorize fault34.
