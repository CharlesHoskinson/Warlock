# Astra process review

The loop optimized preservation and qualification throughput while failing to force visible product delivery. Its safety mechanisms contain real engineering value; their scheduling became the problem. “Zero original requirements completed” is unproved, and replacing it with inflated completion would be equally wrong.

## Severity-ranked findings

**Critical — the stopping condition exists only at whole-release scale.** `inputs/docs/warlock-build-loop/v1/INSTRUCTIONS.md`, “Each iteration,” orders compilation, CPU/decoder/replay/fuzz, Quint, native qualification, frozen derivatives and publication before advancing. `inputs/docs/elm-roadmap/BUILD-LOOP.md` repeats this and says advance immediately. Neither imposes a bounded economic stop on prerequisite discovery, defines a minimum delivered behavior per interval, or limits qualification-only iterations. “Continue independent CPU work” while native admission waits supplies an effectively infinite substitute backlog. The agent should have recognized that loophole rather than interpreting continued activity as continued delivery.

**Critical — known user-facing gaps lose to invented acceptance expansion.** The current combined restart report explicitly says popup-dismissal focus restoration is unqualified, while qualifying fourteen model scenarios and seven supervisor refusal checks on unchanged production source. Its handoff immediately chooses another preview-uncertainty contract. That decision needs an original-scenario dependency argument; it does not follow merely because another CONTROL obligation can be written. Meanwhile `implementation/warlock-preview-provider-v143/native/controlled-preview-host.h:141` always sets popup opacity to zero. A safely invisible preview is useful infrastructure, not a delivered preview. Simply deleting that curtain would also be unacceptable: implement and prove the missing reveal condition.

**High — archival identity is being used as the development architecture.** Mandatory fresh derivatives plus repeated full freezing/publication produce enormous churn and scattered source ownership. The 24-hour packet records 90 commits, 50 with zero classified product-source paths. Summed path classifications include 198,514 QA and 14,780 product-source entries; these are repeated per-commit path occurrences, not unique files or changed behavior. Latest window-restart and combined-restart reports both reverify a 119-command build with no production C/Elm changes. ABI provenance does not require compiling unchanged artifacts or copying a whole application after each fixture adjustment. Evidence preservation does not require duplicating evidence.

**High — reporting cannot answer the user's question.** The integration state is dated October 5 and still names v656; its empty `completedRequirementIds` cannot measure October 7 work. Existing taskbar dispatch implements zero/single/group decisions (`Taskbar.elm:29`), shell statuses distinguish Pending/Unknown/Refused (`Shell.elm:68`), and native restart reports contain genuine bounded successes. Source deltas v141/v143 changed production failure/drain handling. Those facts contradict “nothing implemented,” but do not establish complete EARS acceptance. The required repair is original-scenario adjudication, not another cumulative check count.

**High — authorizations and review authority blur.** Existing status records repeatedly describe source-only reviews as approving a next campaign. A reviewer can identify a defect or missing prerequisite; it should not manufacture an additional permission hierarchy. Preserve actual protected-launcher and activation requirements, but demand a specific original requirement or demonstrated safety defect for every new gate.

## Exact replacement operating rules

1. **WIP = one integrated product slice**, with one explicitly named original scenario set, user-visible result, source candidate and completion oracle. Pick from the frozen 242/417 baseline. Supporting safety work must name the scenario it unblocks; CONTROL work earns no original completion by itself.
2. Start with a compact current-state record, original requirement text, selected evidence index and relevant source diff. Do not reread full historical handoffs every iteration. Maintain one current decision ledger; keep historical artifacts immutable and reference their hashes.
3. Develop in one owned integration worktree derived from the current coherent tuple. Existing frozen directories remain untouched. Commit incremental changes; create a reproducible source manifest for a candidate campaign, not another wholesale source copy for every correction. Reuse unchanged content by immutable reference. Never rewrite held evidence to make a new claim.
4. Validate in proportion to change: compile changed targets; run the direct behavioral regression and one meaningful negative/lifecycle case. Add model exploration or fuzzing for changed state-machine/security boundaries, not automatically for every fixture or document. Native behavior requires its native oracle on the exact owning ABI, through the existing serialized protected launcher. Reuse unchanged build outputs only with complete input/toolchain identity. Broaden tests once at integration or when a concrete dependency/failure warrants it.
5. Permit at most **two qualification-only iterations or 45 minutes without a production fix or original-scenario verdict**. Then stop that branch of investigation, write the precise blocker/counterexample, and choose a bounded original behavior that can advance. A safety blocker stays blocked; the timer never authorizes bypass. Do not mark the whole goal blocked while independent product work remains.
6. Close an original scenario when its own oracle and evidence scope match; close an EARS requirement when all its applicable scenarios and verification obligations pass. Track implemented/unverified, scenario accepted, requirement accepted, integration accepted and release accepted separately. Full-release failure must not reopen unrelated accepted scenarios. Candidate closure audits include ELM-ARC-001 and ELM-REN-001, whose manifest/ledger obligations may already have evidence; verify before marking them done.
7. Report every 30 minutes: original IDs changed/accepted, demonstrated behavior, exact unresolved blocker, elapsed time and available token telemetry, next runnable action. Report unavailable telemetry as unavailable. No progress credit for files, commits, checks, reviewers or publications. No new plugins or standing review panels.

Retain native ABI matching, serial isolated GUI campaigns, original deadlines and clocks, identity/lease and Unknown/no-replay protections, single Elm policy authority, real presentation evidence, drafts, reversible deployment and required activation authorization.
