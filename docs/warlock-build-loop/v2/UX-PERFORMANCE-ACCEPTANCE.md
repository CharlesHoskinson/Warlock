## Adopted MVP review criteria — not measured P0 budgets

The user appointed this owner to set numeric UX criteria. The following are **new working MVP acceptance criteria**, not historical limits, measured baselines, or a replacement for P0 freeze. They apply to an identified physical, hardware-accelerated reference desktop with at least four physical CPU cores, 16 GiB RAM, SSD, a supported GPU and a 60 Hz or faster output. Record exact CPU, GPU/driver/backend, power profile, refresh/scale, display path, build, memory and catalog fixture; do not label a software VM as this hardware class. Stricter original or frozen criteria always apply. The thresholds are engineering allocations chosen to bound noticeable waiting and tail stalls, not claims of a published universal human-perception boundary. At 60 Hz, 100 ms spans six refresh opportunities; 200 ms spans twelve. Validate and revise only through the existing baseline/budget process, retaining the original and all measurements.

For each row, pass requires the correct current state visibly presented within **both** limits; the p50 is recorded, not an extra pass threshold. The input origin is the verified physical/native input timestamp **before internal queueing and policy admission**, never the time the application finally accepts or processes it. Include queueing, loading and refusal feedback in end-to-end measurements; retain internal stage timestamps only as separate diagnostic segments. Use >=300 independent warm actions per workload and fixture class, distributed across >=3 restarts; nearest-rank quantiles and all individual samples retained. Cold startup uses >=30 independent cold starts, report p50/p95 and maximum; p99 from 30 samples is descriptive only and cannot support a p99 acceptance claim. Count failures, timeouts and missing presentations in the denominator; never silently drop them or calculate a pass solely from successes.

| --- | ---: | ---: | --- |
| Physical/native click/key timestamp before internal queueing → first meaningful, correctly styled shell/popup feedback, including a reachable loading or refusal state | 100 ms | 200 ms | Cold process launch → first usable, correctly styled interactive shell: p95 <= 2 s, max <= 3 s. A white or unresponsive frame is not usable. |

| Reversible motion or output transfer input → first correct visible response | 100 ms | 200 ms | Measure completion and full frame sequence separately; preserve current output generation and original deadlines. |

Use repeatable fixtures: small = 62 entries (matching observed MVP cardinality, with synthetic names where privacy requires); large = 2,048 valid entries, the present `Catalog.elm` decoder ceiling. Fix catalog bytes/hash, ordering, query set, hit/no-match mix and locale. Exercise sequential typing, clear, refresh during typing, rapid reversal, keyboard and pointer, cold/warm caches, 100% and 200% text, normal and reduced motion, idle and CPU/IO load. Test multilingual/IME composition without executing text; include actual native IME and assistive technology for their own original gates. Correctness, selection ordering, focus, visible status, no unintended launch and accessible names/announcements are mandatory: a fast wrong result fails.

### Motion and resource working targets

For a fixed-refresh physical reference output, record each independent presentation timestamp, expected refresh period, frame interval distribution, deadline misses and longest gap. During a scripted continuous motion of >=10 s, the provisional MVP target is **p99 interval <= 2 refresh periods**, **missed refresh opportunities <= 1%**, and **no gap > 50 ms**; evaluate each refresh rate separately, including the actual 240 Hz path when available. A missed opportunity is a refresh interval without the expected changing frame, not a repeated static frame. At 240 Hz two periods are 8.333 ms. This is an engineering smoothness target; the frozen native cadence/baseline budget and every original motion oracle still apply. Calibrate timestamp precision and instrument overhead before relying on a threshold; do not infer hardware cadence from browser animation callbacks or a VM.

As provisional investigation thresholds for the same identified physical reference class, measure the entire Warlock-owned process group: idle average <= **5% of one logical CPU**, <= **100 wakeups/s**, summed PSS <= **512 MiB**, summed private memory <= **384 MiB**; a 30-minute idle/interaction soak has private-memory growth <= **32 MiB** after a 5-minute warm-up and no monotonic unbounded object/FD/helper growth. Where PSS is available also record per-process RSS and private dirty/clean; do not sum RSS as unique memory. Measure cumulative uploaded/copied bytes and MiB/s per workload; target closed-preview steady state **0 recurring preview acquisitions/uploads** after the separately frozen quiescence interval. Resource values are initial engineering ceilings, not existing frozen limits or proof that the host fits them. Record wattage where the device exposes attributable, calibrated readings; shared system power is reported as paired whole-system delta, not claimed as process power. Missing capability requires a reasoned exclusion and blocks any applicable original gate.

Regression working criterion for each applicable latency quantile: candidate minus same-machine current-shell baseline <= **max(5 ms, 10% of baseline)**; CPU, wakeups, memory, energy and upload/copy totals <= **max(10% of baseline, declared instrument resolution)**. Absolute criteria and regression criteria must both pass. Paired runs use the same workload, load, output, power profile, driver and cold/warm definition. The 5 ms floor limits noise sensitivity, not permission to waive absolute limits. Zero baseline does not make a missing measurement pass; define the instrument resolution before running and retain it. If an original recorded budget is stricter, use it. These values are provisional comparisons until measured baselines and applicable P0 fields are frozen in the existing budget record.

## Measurement and evidence recipe

1. Bind each run to immutable source commit plus dirty-source hashes, executable/generated Elm and dependent library hashes, runtime/ABI, provider, compositor/output, actual adapter/driver/backend, machine/VM identity, process-group membership and start/end times. Record fixture identity and seed, cache condition, exact workload and input timestamps, logging level, load, exclusions, sample count and retained raw evidence. No sensitive user text or credentials.
2. Establish clock provenance and calibration. Input and presentation timestamps must share a verified monotonic clock or a measured mapping with an error bound small enough for the threshold; retain uncertainty and calibration. Physical input → independent presentation: use a verified native input timestamp plus compositor presentation feedback tied to the actual output/frame, or a calibrated input-trigger/photodiode or high-speed camera showing both event and pixels. A compositor callback is acceptable only if its semantics independently establish the displayed output, not merely buffer submission. Record absence, disconnects and censored observations. Keep a sequence ID correlating input, state, frame and output without treating identity as proof of paint.
3. Record process creation/exit throughout, including renderer and helper descendants; sample CPU time deltas, wakeups, RSS/PSS/private memory, allocations/FDs, upload/copy bytes, GPU memory where attributable, and missed frames. Record GC pauses, IPC queue/send/receive, Elm update/view and render/paint stages as **diagnostic segments**, not substitute end-to-end times. Compare profiling off/on using matched interleaved runs; record absolute and percentage observer overhead, instrumentation loss and the observer's own resource cost. Do not subtract unvalidated overhead from individual samples.
4. Preserve raw monotonic samples and reproducible aggregation, including failed/time-out/censored samples and the independently observed pixel/state. Report n, p50/p95/p99 and max with chosen quantile method; qualify p99 with its sample size and tail uncertainty. Predeclare exclusions (e.g. external interruption), preserve excluded data and reason, and do not exclude slow but valid work. Check correct output and state for each measured success. Use paired baseline/candidate workloads and retain both manifests and results. A high variance or insufficient clock precision is **inconclusive**, not PASS.
5. Enter results in the active original-scenario/contributor records and existing workload matrix with exact applicable limit and baseline; keep current `STATE`/ledger ownership with root. All applicable absolute and regression fields need numeric values, units and explicit justified exclusions. Maintain physical input, AT, IME, native presentation, output-transfer, 240 Hz hardware, GPU, original deadline and release dispositions independently.

### What the current software VM can and cannot establish

The retained run-08 image shows `qvxz9` in the field alongside no-match text; the physical script records click and five QMP key attempts. A separate observation displayed 62 actual catalog entries. Pending input can overlay an older authoritative projection, so this image alone does not prove the no-match result corresponds to the final accepted query; correlate a source-bound authoritative projection with the independently displayed result. The earlier run-04 white frame and run-07 inert early click remain observations, not a proven cause. The 3 s settle and 120 ms hold are test setup. Neither commands nor local writes, HTTP responses, DOM state, renderer queue acknowledgements or coarse screenshot intervals are independent presentation timestamps. Host and guest monotonic clocks differ: do not subtract them without a measured mapping. The 28 s trial/26.4 s mapped interval is a lifetime observation, not response latency.

Root may use a reviewed, bounded VM fixture to identify ordering, correctness, persistent white/inert states, query/focus, process-tree resource trends and **same-guest-clock diagnostic** stage durations; retain software-rendering identity, scheduler/load, observer overhead and failures. A correlated guest native presentation event or calibrated capture can give a VM-specific input-to-visible measurement only when its display semantics and clock mapping are verified. VM results never establish physical GPU performance, actual 240 Hz cadence, physical end-to-end latency, hardware power, native AT/IME or release acceptance. Do not relax the physical criteria to fit this VM.

## Prioritized current-slice review

1. **First usable frame / early input:** independently correlate the first visible non-white usable frame with readiness and hit-test allocation; test a click immediately after that event and a click before it. A control must work when visibly enabled or provide visible loading/unavailable feedback; no speculative 72-versus-56 allocation diagnosis without evidence. The 72-pixel GTK request is not a child allocation receipt; review a child allocation/hit-target observer and record scale and actual geometry. Do not hide delayed readiness with a fixed sleep.
2. **Search tail and correctness:** profile the actual path before optimizing. `Catalog.search` folds each entry's name and tokens for each query and the decoder permits 2,048 entries. `Surface` separately calls it for visible controls and no-match status; page-count paths also call it. These are potential costs, not a measured bottleneck or a proven invocation count for each event. If confirmed, consider sharing derived results and revision-bound precomputed folded fields or bounded caching while preserving exact/prefix/token ranking, localization, identities, current-generation checks and invalidation; compare raw production-route sequences, focus and IME before/after. No second search authority. Record pending input/composition separately from the authoritative query/result pair.
3. **Refresh and lifetime:** instrument catalog-request → response → current Elm update → independently visible results, alongside IPC queue, GC and whole-process sampling; verify old responses cannot overwrite newer queries. Keep delayed operations visibly pending, independently interactive and safe; avoid duplicate commands or fabricated success. Retain a repeatable no-match/current-query test with no application launch.
