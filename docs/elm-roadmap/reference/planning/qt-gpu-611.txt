<h2 id="audio-and-video-codecs">Audio and Video Codecs<a class="plink" href="#audio-and-video-codecs" title="Direct link to this headline"></a></h2>
<p>Qt WebEngine supports the MPEG-4 Part 14 (MP4) file format only if the required proprietary audio and video codecs, such as H.264 and MPEG layer-3 (MP3), have been enabled. Proprietary codecs can be enabled by passing the following option to the <code translate="no">configure</code> tool when configuring Qt:</p>
<div class="pre"><pre class="cpp plain" translate="no">-webengine-proprietary-codecs</pre></div>
<p>For example, the following option could be passed when configuring Qt for building it at the top level:</p>
<div class="pre"><pre class="cpp plain" translate="no">configure -webengine-proprietary-codecs</pre></div>
<p>The actual encoding and decoding is performed by Chromium.</p>
<p>For more information, see <a href="configure-options.html">Qt Configure Options</a>.</p>
<p>When using cmake to build just the Qt WebEngine module, the following command can be used to configure and build (in this example, the Qt WebEngine source code is located in <code translate="no">C:\qt\qtwebengine</code>):</p>
<div class="pre"><pre class="cpp plain" translate="no">qt-configure-module C:\qt\qtwebengine -webengine-proprietary-codecs
cmake --build . --parallel</pre></div>
<div class="admonition warning">
<p><b>Warning: </b>When distributing proprietary codec libraries, you must acquire licenses for them.</p>
</div>
<p><a href="http://ffmpeg.org/">FFmpeg</a> is a cross-platform solution to record, convert, and stream audio and video. It can be configured for use with several codecs, which rises licensing issues during distribution with the codec libraries. For some codecs, open source implementations, such as <a href="http://www.openh264.org/">OpenH264</a>, are available.</p>
<h2 id="chromium-devtools">Chromium DevTools<a class="plink" href="#chromium-devtools" title="Direct link to this headline"></a></h2>
<p>The Chromium DevTools provide the ability to inspect and debug layout and performance issues of any web content.</p>
<p>This feature can be tested by launching a Qt WebEngine application with the command line option <code translate="no">--remote-debugging-port=[your-port]</code> or by setting the environment variable <code translate="no">QTWEBENGINE_REMOTE_DEBUGGING</code> and then using a Chromium-based browser or a Qt WebEngine application (such as <a href="qtwebengine-webenginewidgets-simplebrowser-example.html">Simple Browser</a> or <a href="qtwebengine-webenginequick-quicknanobrowser-example.html">Nano Browser</a>) to connect to <code translate="no">http://localhost:[your-port]</code>.</p>
<div class="admonition note">
<p><b>Note: </b>Any <a href="qml-qtwebengine-webengine.html" translate="no">WebEngine</a> command line options should be specified after the <code translate="no">--webEngineArgs</code> option, which is used to separate the user's application specific options from the <a href="qml-qtwebengine-webengine.html" translate="no">WebEngine</a>'s ones.</p>
</div>
<div class="pre"><pre class="cpp plain" translate="no">--webEngineArgs --remote-debugging-port=5000</pre></div>
<p>To avoid WebSocket errors during remote debugging, add an additional command-line argument <code translate="no">--remote-allow-origins=&lt;origin&gt;[,&lt;origin&gt;, ...]</code>, where <code translate="no">&lt;origin&gt;</code> refers to the request origin. Use <code translate="no">--remote-allow-origins=*</code> to allow connections from all origins. If nothing is specified, Qt WebEngine will add <code translate="no">--remote-allow-origins=*</code> to command-line arguments when remote-debugging is enabled, thereby allowing requests from all origins.</p>
<p>The Chromium DevTools page can also be shown within the application. To set this up, you can call either <a href="qwebenginepage.html#setInspectedPage" translate="no">QWebEnginePage::setInspectedPage</a>() to the page to be inspected, which implicitly loads the DevTools into the <code translate="no">this</code> page, or <a href="qwebenginepage.html#setDevToolsPage" translate="no">QWebEnginePage::setDevToolsPage</a>() to let the <code translate="no">this</code> page be inspected.</p>
<p>The respective QML properties are <a href="qml-qtwebengine-webengineview.html#devToolsView-prop" translate="no">WebEngineView.devToolsView</a> and <a href="qml-qtwebengine-webengineview.html#inspectedView-prop" translate="no">WebEngineView.inspectedView</a>.</p>
<p>For more information, see <a href="qtwebengine-debugging.html">Qt WebEngine Debugging and Profiling</a>.</p>
<h2 id="client-certificates">Client Certificates<a class="plink" href="#client-certificates" title="Direct link to this headline"></a></h2>
<p>Some web servers, in particular many intranet sites, require the client to authenticate itself with a certificate, called a <i>client certificate</i>. Qt WebEngine will read the client certificates installed in the system settings in macOS and Windows, and on Linux those installed into the NSS database. Certificates can be installed into the NSS database using the <code translate="no">pk12util</code> tool.</p>
<p>By default, Qt WebEngine will not offer any client certificates to servers, as doing so uniquely identifies the user and might violate privacy expectations.</p>
<p>To activate support for client certificates, an application needs to listen to the <a href="qwebenginepage.html#selectClientCertificate" translate="no">QWebEnginePage::selectClientCertificate</a> or <a href="qml-qtwebengine-webengineview.html#selectClientCertificate-signal" translate="no">WebEngineView.selectClientCertificate</a> signals and select one of the offered certificates. For applications that can navigate to untrusted web sites, it is recommended to always give the user a choice before uniquely identifying them to a remote server.</p>
<p>In addition to the client certificate stored in system settings, Qt WebEngine offers also the in-memory store. The <a href="qwebengineclientcertificatestore.html" translate="no">QWebEngineClientCertificateStore</a> instance can be obtained with the <a href="qwebengineprofile.html#clientCertificateStore" translate="no">QWebEngineProfile::clientCertificateStore</a>() method. An application can use this class to add a new certificate with a <a href="qwebengineclientcertificatestore.html#add" translate="no">QWebEngineClientCertificateStore::add</a>() call. Note that during the <code translate="no">selectClientCertificate</code> calls, Qt WebEngine lists both system and in-memory stored clients certificates.</p>
<p>The actual validation and use of certificates is performed by Chromium libraries.</p>
<p>See also <a href="qtwebengine-webenginewidgets-clientcertificate-example.html">Client Certificate Example</a> for more implementation details.</p>
<h2 id="custom-schemes">Custom Schemes<a class="plink" href="#custom-schemes" title="Direct link to this headline"></a></h2>
<p>Qt WebEngine makes it possible for the application to define its own custom URL schemes with specialized security policies and transport mechanisms.</p>
<p>Custom schemes can be used to implement alternative network protocols with all the usual web security policies, privileged internal schemes for displaying user interface components or debugging information, sandboxed schemes with extra restrictions, and so on.</p>
<p>The handling of custom schemes is performed primarily by Chromium.</p>
<p>For more information, see <a href="qwebengineurlscheme.html" translate="no">QWebEngineUrlScheme</a> and <a href="qwebengineurlschemehandler.html" translate="no">QWebEngineUrlSchemeHandler</a>.</p>
<h2 id="drag-and-drop">Drag and Drop<a class="plink" href="#drag-and-drop" title="Direct link to this headline"></a></h2>
<p>Qt WebEngine supports HTML5 drag and drop.</p>
<p>This feature can be tested by opening an HTML5 drag and drop demo, such as <a href="http://html5demos.com/drag">HTML5 Demos - Drag and Drop</a>, <a href="http://html5demos.com/drag-anything">HTML5 Demos - Simple Drag and Drop</a>, or <a href="http://html5demos.com/dnd-upload">HTML5 Demos - Drag and Drop, Automatic Upload</a>, in <a href="qtwebengine-webenginewidgets-simplebrowser-example.html">Simple Browser</a> or <a href="qtwebengine-webenginequick-quicknanobrowser-example.html">Nano Browser</a>.</p>
<p>Dragging files into the web view is not actually part of HTML5, but it is supported. It can be tested by opening <a href="http://html5demos.com/file-api">HTML5 Demos - File API</a>.</p>
<p>The actual implementation of this feature is provided by Chromium.</p>
<h2 id="favicon">Favicon<a class="plink" href="#favicon" title="Direct link to this headline"></a></h2>
<p>Qt WebEngine supports the web site URL icon, <i>favicon</i>. Each icon is stored in the internal database for each <a href="qwebengineprofile.html" translate="no">QWebEngineProfile</a> and can be accessed using a <a href="qwebenginepage.html#icon-prop" translate="no">QWebEnginePage::icon</a>() call or a <a href="qml-qtwebengine-webengineview.html#icon-prop" translate="no">WebEngineView.icon</a> property for the currently loaded content.</p>
<p>Moreover Qt WebEngine provides API for accessing already stored icons in the internal profile's database. The database implementation itself is provided by Chromium.</p>
<div class="admonition note">
<p><b>Note: </b>The icon database is not available for off-the-record profiles.</p>
</div>
<h3 id="qml-favicon-handling">QML Favicon Handling<a class="plink" href="#qml-favicon-handling" title="Direct link to this headline"></a></h3>
<p>For accessing icons a <code translate="no">QQuickImageProvider</code> is registered. This provider can be accessed by a special URL where the scheme is "image:" and the host is "favicon".</p>
<div class="pre"><pre class="qml prettyprint" translate="no"><span class="type"><a href="qml-qtquick-image.html" translate="no">Image</a></span> {
    <span class="name">source</span>: <span class="string">"image://favicon/url"</span>
}</pre></div>
<p>The <code translate="no">url</code> can be the URL of the favicon:</p>
<div class="pre"><pre class="qml prettyprint" translate="no"><span class="type"><a href="qml-qtquick-image.html" translate="no">Image</a></span> {
    <span class="name">source</span>: <span class="string">"image://favicon/https://www.qt.io/hubfs/2016_Qt_Logo/qt_logo_green_rgb_16x16.png"</span>
}</pre></div>
<p>The <code translate="no">url</code> also can be a page URL to access its icon:</p>
<div class="pre"><pre class="qml prettyprint" translate="no"><span class="type"><a href="qml-qtquick-image.html" translate="no">Image</a></span> {
    <span class="name">source</span>: <span class="string">"image://favicon/https://www.qt.io/"</span>
}</pre></div>
<p>If more than one icon is available, the <a href="qml-qtquick-image.html#sourceSize-prop" translate="no">Image::sourceSize</a> property can be specified to choose the icon with the desired size. If <a href="qml-qtquick-image.html#sourceSize-prop" translate="no">Image::sourceSize</a> is not specified or 0, the largest available icon will be chosen.</p>
<p>The image provider looks up the requested icon in the existing <a href="qml-qtwebengine-webengineview.html" translate="no">WebEngineView</a> instances. First, it tries to match the currently displayed icons. If no match has been found it requests the icon from the database. Each profile has its own icon database and it is stored in the persistent storage thus the stored icons can be accessed without network connection too. The icon must be previously loaded to be stored in the database.</p>
<h3 id="c-favicon-handling">C++ Favicon Handling<a class="plink" href="#c-favicon-handling" title="Direct link to this headline"></a></h3>
<p>A user can request an icon from the previously loaded content for each <a href="qwebengineprofile.html" translate="no">QWebEngineProfile</a> using the <a href="qwebengineprofile.html#requestIconForPageURL" translate="no">QWebEngineProfile::requestIconForPageURL</a>() or <a href="qwebengineprofile.html#requestIconForIconURL" translate="no">QWebEngineProfile::requestIconForIconURL</a>() calls. Note that the profile's database is stored in the persistent storage and can be accessed without a network connection.</p>
<h2 id="fullscreen">Fullscreen<a class="plink" href="#fullscreen" title="Direct link to this headline"></a></h2>
<p>Qt WebEngine supports viewing web content in fullscreen mode. For more information, see <a href="qml-qtwebengine-webenginesettings.html#fullscreenSupportEnabled-prop" translate="no">WebEngineSettings.fullscreenSupportEnabled</a>, <a href="qml-qtwebengine-webengineview.html#fullScreenRequested-signal" translate="no">WebEngineView.fullScreenRequested</a>, <a href="qwebenginesettings.html#WebAttribute-enum" translate="no">QWebEngineSettings::FullScreenSupportEnabled</a>, and <a href="qwebenginepage.html#fullScreenRequested" translate="no">QWebEnginePage::fullScreenRequested</a>.</p>
<p>This feature can be tested by playing a video from YouTube in <a href="qtwebengine-webenginewidgets-videoplayer-example.html">Video Player</a> or <a href="qtwebengine-webenginequick-quicknanobrowser-example.html">Nano Browser</a>, and clicking the full screen icon to go into fullscreen mode.</p>
<h2 id="hardware-acceleration">Hardware Acceleration<a class="plink" href="#hardware-acceleration" title="Direct link to this headline"></a></h2>
<p>Qt WebEngine tries to use hardware acceleration for rendering web content whenever possible. The actual rendering is performed by Chromium, and the final image is produced by Chromium's compositor, which makes use of modern GPU APIs such as OpenGL, Vulkan, Metal, or Direct3D, depending on the platform and available drivers.</p>
<p>This final image is then imported by Qt WebEngine into the Qt rendering pipeline using GPU interoperability, allowing efficient sharing of GPU resources without unnecessary copies. The imported image is passed to the <a href="qtquick-visualcanvas-scenegraph.html">Qt Quick Scene Graph</a>, which also performs hardware-accelerated rendering through the Qt Rendering Hardware Interface (RHI).</p>
<p>While both Qt and Chromium rely on GPU acceleration, they may not necessarily use the same graphics API. In practice, Qt WebEngine attempts to align Chromium’s GPU backend with the one used by Qt when possible, defaulting to Qt’s chosen backend configuration to ensure compatibility and optimal performance, though it is possible to manually override these defaults if needed.</p>
<p>When hardware acceleration is not available or fails, Qt WebEngine automatically tries to fall back to software rendering.</p>
<h3 id="force-use-of-software-rendering">Force use of software rendering<a class="plink" href="#force-use-of-software-rendering" title="Direct link to this headline"></a></h3>
<p>The automatic fallback to software rendering is not always possible, and Qt WebEngine may fail to properly display web content or may exit with an error message. In such cases, it maybe necessary to explicitly disable hardware acceleration and use software rendering instead.</p>
<p>There are multiple ways to force software rendering:</p>
<ul>
<li>Disable hardware acceleration in Chromium:<div class="pre"><pre class="cpp plain" translate="no">export QTWEBENGINE_CHROMIUM_FLAGS=--disable-gpu</pre></div>
</li>
<li>Disable hardware acceleration in <a href="qtquick-visualcanvas-scenegraph.html">Qt Quick Scene Graph</a>:<div class="pre"><pre class="cpp plain" translate="no">export QT_QUICK_BACKEND=software</pre></div>
</li>
</ul>
<h3 id="changing-the-graphics-api-backend-in-qt">Changing the graphics API backend in Qt<a class="plink" href="#changing-the-graphics-api-backend-in-qt" title="Direct link to this headline"></a></h3>
<p>There are two ways to choose the graphics API backend:</p>
<ul>
<li>Set <code translate="no">QSG_RHI_BACKEND</code> environment variable before launching application.</li>
<li>Call <a href="qquickwindow.html#setGraphicsApi" translate="no">QQuickWindow::setGraphicsApi</a>() in combination with <a href="qsgrendererinterface.html#GraphicsApi-enum" translate="no">QSGRendererInterface::GraphicsApi</a> before constructing the first <a href="qquickwindow.html" translate="no">QQuickWindow</a>.</li>
</ul>
<p>For more details, see <a href="qtquick-visualcanvas-scenegraph-renderer.html#rendering-via-the-qt-rendering-hardware-interface">Rendering via the Qt Rendering Hardware Interface</a>.</p>
<h3 id="changing-the-graphics-api-backend-in-chromium">Changing the graphics API backend in Chromium<a class="plink" href="#changing-the-graphics-api-backend-in-chromium" title="Direct link to this headline"></a></h3>
<p>Changing Chromium’s graphics API backend is generally not recommended, as it may cause compatibility issues or inconsistent rendering behavior. Whenever possible, prefer using the <code translate="no">QSG_RHI_BACKEND</code> environment variable instead. However, it may be necessary in some cases for debugging or as a temporary workaround for driver-specific problems.</p>
<p>To override Chromium's backend, set the <code translate="no">QTWEBENGINE_CHROMIUM_FLAGS</code> environment variable to pass the corresponding Chromium command line flags, such as <code translate="no">--use-gl=</code> or <code translate="no">--use-angle=</code>.</p>
<p>In Qt WebEngine, Chromium currently uses the <i>ANGLE</i> backend by default on all platforms where hardware acceleration is supported. ANGLE is a cross-platform graphics abstraction layer in Chromium which hides the underlying native graphics backend.</p>
<p>The default configuration Qt WebEngine uses is this:</p>
<div class="pre"><pre class="cpp plain" translate="no">export QTWEBENGINE_CHROMIUM_FLAGS="--use-gl=angle --use-angle=default"</pre></div>
<p>If ANGLE crashes under a specific configuration, it can be completely disabled while still using Vulkan for hardware-accelerated rendering:</p>
<div class="pre"><pre class="cpp plain" translate="no">export QTWEBENGINE_CHROMIUM_FLAGS="--use-gl=stub --enable-features=Vulkan --use-vulkan=native"</pre></div>
<div class="admonition note">
<p><b>Note: </b>Certain features such as <a href="qtwebengine-features.html#webgl">WebGL</a> may not work with a custom configuration like this.</p>
</div>
<p>Alternatively, the following configuration uses Vulkan for rendering while keeping ANGLE enabled for <a href="qtwebengine-features.html#webgl">WebGL</a> support:</p>
<div class="pre"><pre class="cpp plain" translate="no">export QTWEBENGINE_CHROMIUM_FLAGS="--use-gl=angle --enable-features=Vulkan --use-vulkan=native"</pre></div>
<p>For more details about the corresponding Chromium command line flags, see Chromium's source code: <a href="https://chromium.googlesource.com/experimental/chromium/src/+/lkgr/ui/gl/gl_switches.cc">//ui/gl/gl_switches.cc</a></p>
<h3 id="nvidia-on-linux">NVIDIA on Linux<a class="plink" href="#nvidia-on-linux" title="Direct link to this headline"></a></h3>
<p>On Linux systems with an NVIDIA GPU, Chromium is forced to use Vulkan for rendering.</p>
<p>Qt WebEngine uses GBM buffer objects to import textures from Chromium into Qt's graphics pipeline. However, NVIDIA drivers currently do not support allocating these buffer objects. As a workaround, Qt WebEngine forces Chromium to render with Vulkan and imports the textures using Vulkan interoperability.</p>
<div class="admonition note">
<p><b>Note: </b>Qt itself is not forced to use Vulkan. Chromium uses the <code translate="no">--use-gl=angle --enable-features=Vulkan --use-vulkan=native</code> configuration.</p>
</div>
<h3 id="enable-logging-and-troubleshooting">Enable logging and troubleshooting<a class="plink" href="#enable-logging-and-troubleshooting" title="Direct link to this headline"></a></h3>
<p>When a rendering issue occurs, it is important to know the failing configuration and the current state of hardware acceleration in order to investigate and report the problem effectively.</p>
<p>The easiest way to check this information is to load the <code translate="no">chrome://gpu</code> internal page and analyze its content. However, this page may not always be readable or available during a rendering issue.</p>
<p>Qt WebEngine provides logging categories that can be enabled to dump detailed graphics information:</p>
<ul>
<li><code translate="no">qt.webenginecontext</code> logs how Qt WebEngine was initialized, the detected GPU, and the graphics configuration.</li>
<li><code translate="no">qt.webengine.compositor</code> logs the configuration used by Chromium and the steps Qt WebEngine takes to import textures into Qt's graphics pipeline.</li>
</ul>
<p>To enable these logs, set the <code translate="no">QT_LOGGING_RULES</code> environment variable, for example:</p>
<div class="pre"><pre class="cpp plain" translate="no">export QT_LOGGING_RULES="qt.webenginecontext=true;qt.webengine.compositor=true"</pre></div>
<div class="admonition note">
<p><b>Note: </b>If the <code translate="no">QSG RHI Device</code> used by Qt and the <code translate="no">GL Renderer</code> used by Chromium differ, it indicates that Qt and Chromium are using different GPUs in a multi-GPU system, which is currently not supported.</p>
</div>

<h2 id="html5-drm">HTML5 DRM<a class="plink" href="#html5-drm" title="Direct link to this headline"></a></h2>
<p>Qt WebEngine supports displaying DRM-protected videos if the <a href="http://www.widevine.com">Widevine CDM</a> plugin has been installed. The plugin comes only in a binary format, so it can hide DRM decryption implementation details. You can obtain it from a third party, or from a Google Chrome installation.</p>
<p>The support for HTML5 DRM is provided by Chromium.</p>
<div class="admonition note">
<p><b>Note: </b>The Widevine plugin is not shipped with Qt WebEngine.</p>
</div>
<p>On startup, Qt WebEngine looks for the <a href="http://www.widevine.com">Widevine CDM</a> plugin in several well-known locations, like the default Google Chrome installation directory, or Linux distro-specific paths. You can also pass the plugin location with <code translate="no">QTWEBENGINE_CHROMIUM_FLAGS</code> using <code translate="no">widevine-path</code>.</p>
<p>On Windows:</p>
<div class="pre"><pre class="cpp plain" translate="no">set QTWEBENGINE_CHROMIUM_FLAGS=--widevine-path="C:/some path/widevinecdm.dll"</pre></div>
<p>On Linux:</p>
<div class="pre"><pre class="cpp plain" translate="no">export QTWEBENGINE_CHROMIUM_FLAGS=--widevine-path="/some path/libwidevinecdm.so"</pre></div>
<p>On macOS:</p>
<div class="pre"><pre class="cpp plain" translate="no">export QTWEBENGINE_CHROMIUM_FLAGS=--widevine-path="/some path/libwidevinecdm.dylib"</pre></div>
<p>The video format most commonly used by DRM services, H.264, requires proprietary audio and video codecs. For more information about enabling the codecs, see <a href="qtwebengine-features.html#audio-and-video-codecs">Audio and Video Codecs</a>.</p>
<p>You can test this feature by playing a video from <a href="http://demo.castlabs.com/">castLabs</a> or <a href="https://bitmovin.com/demos/drm">Bitmovin Player</a> in the <a href="qtwebengine-webenginewidgets-simplebrowser-example.html">Simple Browser</a> or <a href="qtwebengine-webenginequick-quicknanobrowser-example.html">Nano Browser</a> example projects.</p>
<h2 id="html5-geolocation">HTML5 Geolocation<a class="plink" href="#html5-geolocation" title="Direct link to this headline"></a></h2>
<p>Qt WebEngine supports JavaScript Geolocation API with <a href="qtpositioning-index.html">Qt Positioning</a> as a backend. HTML5 geolocation is disabled by default. To explicitly allow it, the application needs to listen to <a href="qwebenginepage.html#permissionRequested" translate="no">QWebEnginePage::permissionRequested</a>. When a permission request with a type of <a href="qwebenginepermission.html#PermissionType-enum" translate="no">QWebEnginePermission::PermissionType::Geolocation</a> is received, you can call <a href="qwebenginepermission.html#grant" translate="no">QWebEnginePermission::grant</a>() on the received object to grant the required permission.</p>
<p>If Qt WebEngine was built with Qt Positioning support then this feature can be tested by using <a href="qtwebengine-webenginewidgets-maps-example.html">Maps</a> and allowing it to find the current position of the user.</p>
<div class="admonition note">
<p><b>Note: </b>On Windows 11, enable settings to grant the maps example access to Windows location services. In the Settings App under <b translate="no">Privacy &amp; Security</b> &gt; <b translate="no">Location</b>, enable <b translate="no">Location services</b>, <b translate="no">Let apps access your location</b> and <b translate="no">Let desktop apps access your location</b>.</p>
</div>
<p>The JavaScript side of the Geolocation API is implemented and provided by Chromium.</p>
<p>See <a href="qtpositioning-index.html">Qt Positioning</a> for a possible backend setup like the GPS or IP based positioning.</p>
<h2 id="html5-permissions">HTML5 Permissions<a class="plink" href="#html5-permissions" title="Direct link to this headline"></a></h2>
<p>Qt WebEngine has support for several types of web feature permissions via the <a href="qwebenginepermission.html" translate="no">QWebEnginePermission</a> API. Permissions can be granted (or denied) to a web domain whenever a page requests potentially sensitive user information, like access to the users' camera or geolocation.</p>
<p>Application developers can choose whether to ask the end user for permission or automatically make the decision for them. Moreover, they can preemptively grant or deny certain permissions, in cases where a known domain is expected to request them.</p>
<p>The <a href="qwebengineprofile.html" translate="no">QWebEngineProfile</a> object stores all permissions that have been granted or denied to individual domains. Unless the current profile is off-the-record, those permissions are stored to disk and recalled the next time an application is opened. However, this behavior can be modified, and developers can choose to only store permissions until application exit, or even to make permission requests trigger every time a website asks for them.</p>
<p>The full list of currently supported web permissions can be found <a href="qwebenginepermission.html#PermissionType-enum" translate="no">in the QWebEnginePermission documentation</a>.</p>
<p>The implementation of permissions logic and the JavaScript Permissions API is provided by Chromium.</p>
<div class="admonition note">
<p><b>Note: </b>Web permissions are different from application permissions, which are governed by the QPermissions API. Web permissions are granted to individual web domains, and not to the full application. However, the two APIs are not mutually exclusive. For example, access to the user's camera and microphone may require granting permission through both APIs.</p>
</div>

<h2 id="page-lifecycle-api">Page Lifecycle API<a class="plink" href="#page-lifecycle-api" title="Direct link to this headline"></a></h2>
<p>Qt WebEngine supports the <a href="https://wicg.github.io/page-lifecycle/spec.html">Page Lifecycle API specification</a>, a work-in-progress extension to the HTML standard for allowing user agents to reduce their resource consumption by freezing or discarding background pages. The feature is implemented by Chromium, and exposed both in the Widgets and QML APIs.</p>
<p>For an example of the QML API in use, see the <a href="qtwebengine-webenginequick-lifecycle-example.html">WebEngine Lifecycle Example</a>.</p>
<h3 id="overview-of-lifecycle-states">Overview of Lifecycle States<a class="plink" href="#overview-of-lifecycle-states" title="Direct link to this headline"></a></h3>
<p>Each <a href="qml-qtwebengine-webengineview.html" translate="no">WebEngineView</a> item (or <a href="qwebenginepage.html" translate="no">QWebEnginePage</a> object) can be in one of three <i>lifecycle states</i>: active, frozen, or discarded. These states, like the sleep states of a CPU, control the resource usage of web views.</p>
<p>The <i>active</i> state is the normal, unrestricted state of a web view. All visible web views are always in the active state, as are all web views that have not yet finished loading. Only invisible, idle web views can be transitioned to other lifecycle states.</p>
<p>The <i>frozen</i> state is a low CPU usage state. In this state, most HTML task sources are suspended (frozen) and, as a result, most DOM event processing and JavaScript execution will also be suspended. The web view must be invisible in order to be frozen as rendering is not possible in this state.</p>
<p>The <i>discarded</i> state is an extreme resource-saving state. In this state, the browsing context of the web view will be discarded and the corresponding renderer subprocess shut down. CPU and memory usage in this state is reduced virtually to zero. On exiting this state the web page will be automatically reloaded. The process of entering and exiting the discarded state is similar to serializing the history of the web view and destroying the view, then creating a new view and restoring its history.</p>
<p>See also <a href="qml-qtwebengine-webengineview.html#LifecycleState-prop" translate="no">WebEngineView::LifecycleState</a>. The equivalent in the Widgets API is <a href="qwebenginepage.html#LifecycleState-enum" translate="no">QWebEnginePage::LifecycleState</a>.</p>
<h3 id="the-lifecyclestate-and-recommendedstate-properties">The <code translate="no">lifecycleState</code> and <code translate="no">recommendedState</code> Properties<a class="plink" href="#the-lifecyclestate-and-recommendedstate-properties" title="Direct link to this headline"></a></h3>
<p>The <a href="qml-qtwebengine-webengineview.html#lifecycleState-propx" translate="no">lifecycleState</a> property of the <a href="qml-qtwebengine-webengineview.html" translate="no">WebEngineView</a> type is a read-write property that controls the current lifecycle state of the web view. This property is designed to place as few restrictions as possible on what states can be transitioned to. For example, it is allowed to freeze a web view that is currently playing music in the background, stopping the music. In order to implement a less aggressive resource-saving strategy that avoids interrupting user-visible background activity, the <a href="qml-qtwebengine-webengineview.html#recommendedState-prop" translate="no">recommendedState</a> property must be used.</p>
<p>The <a href="qml-qtwebengine-webengineview.html#recommendedState-prop" translate="no">recommendedState</a> property of the <a href="qml-qtwebengine-webengineview.html" translate="no">WebEngineView</a> type is a read-only property that calculates a safe limit on the <a href="qml-qtwebengine-webengineview.html#lifecycleState-propx" translate="no">lifecycleState</a> property, taking into account the current activity of the web view. So, in the example of a web view playing music in the background, the recommended state will be <code translate="no">Active</code> since a more aggressive state would stop the music. If the application wants to avoid interrupting background activity, then it should avoid putting the web view into a more aggressively resource-saving lifecycle state than what's given by <a href="qml-qtwebengine-webengineview.html#recommendedState-prop" translate="no">recommendedState</a>.</p>
<p>See also <a href="qml-qtwebengine-webengineview.html#lifecycleState-propx" translate="no">WebEngineView::lifecycleState</a> and <a href="qml-qtwebengine-webengineview.html#recommendedState-prop" translate="no">WebEngineView::recommendedState</a>. The equivalents in the Widgets API are <a href="qwebenginepage.html#lifecycleState-propx" translate="no">QWebEnginePage::lifecycleState</a> and <a href="qwebenginepage.html#recommendedState-prop" translate="no">QWebEnginePage::recommendedState</a>.</p>
<h3 id="the-dom-extensions">The DOM Extensions<a class="plink" href="#the-dom-extensions" title="Direct link to this headline"></a></h3>
<p>The <a href="qml-qtwebengine-webengineview.html#lifecycleState-propx" translate="no">lifecycleState</a> property is connected to the <a href="https://wicg.github.io/page-lifecycle/spec.html">Page Lifecycle API specification</a>, which specifies two new DOM events, <code translate="no">freeze</code> and <code translate="no">resume</code>, and adds a new <code translate="no">Document.wasDiscarded</code> boolean property. The <code translate="no">freeze</code> and <code translate="no">resume</code> events are fired when transitioning from the <code translate="no">Active</code> to the <code translate="no">Frozen state</code>, and vice-versa. The <code translate="no">Document.wasDiscarded</code> property is set to <code translate="no">true</code> when transitioning from the <code translate="no">Discarded</code> state to the <code translate="no">Active</code> state.</p>
<h2 id="print-to-pdf">Print to PDF<a class="plink" href="#print-to-pdf" title="Direct link to this headline"></a></h2>
<p>Qt WebEngine supports printing a web page to a PDF file. For more information, see <a href="qwebenginepage.html#printToPdf" translate="no">QWebEnginePage::printToPdf</a>() and <a href="qml-qtwebengine-webengineview.html#printToPdf-method" translate="no">WebEngineView.printToPdf</a>.</p>
<p>This feature can be tested using <a href="qtwebengine-webenginewidgets-html2pdf-example.html">Html2Pdf</a>.</p>
<p>The implementation of this feature is provided by Chromium.</p>
<h2 id="push-notifications">Push Notifications<a class="plink" href="#push-notifications" title="Direct link to this headline"></a></h2>
<p>Qt WebEngine exposes an API to the JavaScript <a href="https://www.w3.org/TR/push-api/">Push API</a> to subscribe to and receive push notifications. The implementation of this API is provided by Chromium. For more information, see <a href="qwebengineprofile.html#setPushServiceEnabled" translate="no">QWebEngineProfile::setPushServiceEnabled</a>() and <a href="qml-qtwebengine-webengineprofile.html#isPushServiceEnabled-prop" translate="no">WebEngineProfile.setPushServiceEnabled</a>.</p>
<p>This feature can be tested with the <a href="qtwebengine-webenginewidgets-push-notifications-example.html">WebEngine Push Notifications Example</a>.</p>
<h2 id="spellchecker">Spellchecker<a class="plink" href="#spellchecker" title="Direct link to this headline"></a></h2>
<p>Qt WebEngine supports integrating spellchecking support into HTML forms to enable users to submit spellchecked messages. When the user clicks on an underlined misspelled word, the default context menu displays up to four suggestions. Selecting one will replace the misspelled word.</p>
<p>The spellchecker implementation is mainly provided by Chromium.</p>
<p>To be able to check the spelling, the spellchecker needs dictionaries. It supports dictionaries from the <a href="https://sourceforge.net/projects/hunspell/">Hunspell project</a>, but they have to be compiled into a special binary format. A Hunspell dictionary consists of two files:</p>
<ul>
<li>A <code translate="no">.dic</code> file that is a dictionary containing words for the language</li>
<li>An <code translate="no">.aff</code> file that defines the meaning of special flags in the dictionary</li>
</ul>
<p>These two files can be converted into the <code translate="no">bdic</code> format by using the <code translate="no">qwebengine_convert_dict</code> tool that is shipped together with Qt. When the Qt WebEngine spellchecker initializes, it will try to load the <code translate="no">bdict</code> dictionaries and to check them for consistency.</p>
<p>For CMake, you can use the <a href="qt-add-webengine-dictionary.html">qt_add_webengine_dictionary</a> command to convert Hunspell <code translate="no">.dic</code> files into the <code translate="no">.bdic</code> binary format. The command creates a <code translate="no">qtwebengine_dictionaries</code> target, which your project can use a dependency.</p>
<p>By default, Qt WebEngine searches for dictionaries inside the <i>qtwebengine_dictionaries</i> directory relative to the executable if it exists. If it does not exist, it will look in <code translate="no">QT_INSTALL_PREFIX/qtwebengine_dictionaries</code>.</p>
<p>Alternatively, a dictionaries directory path can be set as a value of the <code translate="no">QTWEBENGINE_DICTIONARIES_PATH</code> environment variable, or via the command-line:</p>
<div class="pre"><pre class="cpp plain" translate="no">--webEngineArgs --webengine-dictionaries-path=&lt;path&gt;</pre></div>
<p>When an override is set, the application looks for dictionaries only inside the provided directory, and nowhere else.</p>
<p>On macOS, depending on how Qt WebEngine is configured at build time, there are two possibilities how spellchecking data is found:</p>
<ul>
<li>Hunspell dictionaries (default) - .bdic dictionaries are used, just like on other platforms</li>
<li>Native dictionaries - the macOS spellchecking APIs are used (which means the results will depend on the installed OS dictionaries)</li>
</ul>
<p>Thus, in the macOS Hunspell case, Qt WebEngine will look in the <i>qtwebengine_dictionaries</i> subdirectory located inside the application bundle <code translate="no">Resources</code> directory, and also in the <code translate="no">Resources</code> directory located inside the Qt framework bundle.</p>
<p>To summarize, in case of Hunspell usage, the following paths are considered:</p>
<ul>
<li><code translate="no">QTWEBENGINE_DICTIONARIES_PATH</code>, if set</li>
<li><a href="qcoreapplication.html#applicationDirPath" translate="no">QCoreApplication::applicationDirPath</a>()/qtwebengine_dictionaries or <a href="qcoreapplication.html#applicationDirPath" translate="no">QCoreApplication::applicationDirPath</a>()/../Contents/Resources/qtwebengine_dictionaries (on macOS)</li>
<li>[<a href="qlibraryinfo.html#LibraryPath-enum" translate="no">QLibraryInfo::DataPath</a>]/qtwebengine_dictionaries or path/to/<a href="qtwebenginecore-module.html" translate="no">QtWebEngineCore</a>.framework/Resources/qtwebengine_dictionaries (Qt framework bundle on macOS)</li>
</ul>
<p>Spellchecking is disabled by default and can be enabled per profile by using the <a href="qwebengineprofile.html#setSpellCheckEnabled" translate="no">QWebEngineProfile::setSpellCheckEnabled</a>() method in widget-based applications and the <a href="qquickwebengineprofile.html#spellCheckEnabled-prop" translate="no">WebEngineProfile.spellCheckEnabled</a> property in Qt Quick applications.</p>
<p>The current language used for spellchecking is defined per profile, and can be set using the <a href="qwebengineprofile.html#setSpellCheckLanguages" translate="no">QWebEngineProfile::setSpellCheckLanguages</a>() method or the <a href="qquickwebengineprofile.html#spellCheckLanguages" translate="no">WebEngineProfile.spellCheckLanguages</a> property.</p>
<p>This feature can be tested by building and running the <a href="qtwebengine-webenginewidgets-spellchecker-example.html">Spellchecker Example</a>.</p>
<p>Qt WebEngine can be compiled also without spellchecker support with the use of a <code translate="no">webengine-spellchecker</code> configure switch.</p>
<div class="pre"><pre class="cpp plain" translate="no">qt-configure-module path\to\qtwebengine\sources -no-webengine-spellchecker</pre></div>
<p>For more information, see <a href="configure-options.html">Qt Configure Options</a>.</p>
<h2 id="touch">Touch<a class="plink" href="#touch" title="Direct link to this headline"></a></h2>
<p>Qt WebEngine supports touch devices for navigating and interacting with web pages.</p>
<p>The touch event support in JavaScript API depends on the presence of a touch screen (meaning <code translate="no">ontouchstart</code> and related handlers will be present in the <code translate="no">document.window</code> object if a capable touch device is connected to the system).</p>
<p>Some websites use this API to decide whether they run on a mobile device or on desktop and base their design on it. This can cause unwanted results on touchscreen laptops or other setups that emulate a fake touch device.</p>
<p>Applications can set this feature explicitly with <a href="qwebenginesettings.html#WebAttribute-enum" translate="no">QWebEngineSettings::TouchEventsApiEnabled</a>.</p>
<p>Note that touch events will still be delivered to web pages even if the API is disabled. Dispatching touch events to web pages can be prohibited by installing an event filter object using <a href="qobject.html#installEventFilter" translate="no">QObject::installEventFilter</a> on the <a href="qml-qtwebengine-webengine.html" translate="no">WebEngine</a> view focus proxy object, and filtering out all touch events.</p>
<p>The implementation of this feature is provided by Chromium.</p>
<h2 id="view-source">View Source<a class="plink" href="#view-source" title="Direct link to this headline"></a></h2>
<p>Qt WebEngine supports viewing the HTML source of a web page.</p>
<p>This feature can be used from custom menus or assigned to custom events. For more information, see <a href="qml-qtwebengine-webengineview.html#WebAction-prop" translate="no">WebEngineView::WebAction</a>, and <a href="qwebenginepage.html#WebAction-enum" translate="no">QWebEnginePage::WebAction</a>.</p>
<p>This feature can be tested by opening a web page in <a href="qtwebengine-webenginewidgets-simplebrowser-example.html">Simple Browser</a> or <a href="qtwebengine-webenginequick-quicknanobrowser-example.html">Nano Browser</a>, and then selecting <code translate="no">Page Source</code> in the context menu. The <code translate="no">Page Source</code> context menu entry opens the source view in a new tab.</p>
<p>For opening the source view in the current tab, URLs with <a href="https://www.iana.org/assignments/uri-schemes/prov/view-source">view-source URI scheme</a> are also supported. For example, you can type the following URL to the URL bar to view the HTML source of the qt.io web page:</p>
<div class="pre"><pre class="cpp plain" translate="no">view-source:https://www.qt.io/</pre></div>
<p>Auto-completion of incomplete URLs with <a href="https://www.iana.org/assignments/uri-schemes/prov/view-source">view-source URI scheme</a> makes the usage of this feature more comfortable. For example, the following incomplete URL also loads the source view of the qt.io web page:</p>
<div class="pre"><pre class="cpp plain" translate="no">view-source:qt.io</pre></div>
<p>The implementation of this feature is provided by Chromium.</p>
<h2 id="web-notifications">Web Notifications<a class="plink" href="#web-notifications" title="Direct link to this headline"></a></h2>
<p>Qt <a href="qml-qtwebengine-webengine.html" translate="no">WebEngine</a> supports JavaScript <a href="https://www.w3.org/TR/notifications">Web Notifications API</a>. The application has to explicitly allow the feature by using QWebEnginePage::Notifications or <a class="obsolete" href="qml-qtwebengine-webengineview-obsolete.html#Feature-prop" translate="no">WebEngineView.Notifications</a>.</p>
<p>The implementation of the JavaScript Web Notifications API is provided by Chromium.</p>
<h2 id="webenginedriver">WebEngineDriver<a class="plink" href="#webenginedriver" title="Direct link to this headline"></a></h2>
<p>With WebEngineDriver, you can automate the testing of web sites. WebEngineDriver is based on the Chromium-provided ChromeDriver and can be used the same way. For more information about ChromeDriver and its use, visit <a href="https://chromedriver.chromium.org/">ChromeDriver user site</a>.</p>
<p>WebEngineDriver has slight modifications compared to ChromeDriver to be able to connect to Qt WebEngine based applications. It is compatible with Qt WebEngine example browsers, such as <a href="qtwebengine-webenginewidgets-simplebrowser-example.html">Simple Browser</a> or <a href="qtwebengine-webenginequick-quicknanobrowser-example.html">Nano Browser</a>.</p>
<p>The automation is scripted through a WebDriver client like the <a href="https://www.selenium.dev/">Selenium WebDriver</a>. For example, WebEngineDriver can be used with the Python lanugage bindings of Selenium WebDriver:</p>
<div class="pre"><pre class="cpp prettyprint" translate="no">from selenium import webdriver
from selenium<span class="operator">.</span>webdriver<span class="operator">.</span>chrome<span class="operator">.</span>service import Service

service <span class="operator">=</span> Service(executable_path<span class="operator">=</span><span class="char">'QTDIR/libexec/webenginedriver'</span>)
options <span class="operator">=</span> webdriver<span class="operator">.</span>ChromeOptions()
options<span class="operator">.</span>binary_location <span class="operator">=</span> <span class="char">'path/to/binary'</span>

driver <span class="operator">=</span> webdriver<span class="operator">.</span>Chrome(service<span class="operator">=</span>service<span class="operator">,</span> options<span class="operator">=</span>options)
driver<span class="operator">.</span>get(<span class="string">"http://www.google.com/"</span>)
driver<span class="operator">.</span>quit()</pre></div>
<p>In this example,</p>
<ul>
<li><code translate="no">executable_path</code> has to be set to the WebEngineDriver's binary path</li>
<li><code translate="no">QTDIR</code> is the directory where Qt is installed</li>
<li><code translate="no">options.binary_location</code> has to be set to the application's binary path</li>
</ul>
<div class="admonition note">
<p><b>Note: </b>On Windows: <code translate="no">executable_path='QTDIR/bin/webenginedriver.exe'</code></p>
</div>
<p>Before executing the script, the <code translate="no">QTWEBENGINE_REMOTE_DEBUGGING</code> environment variable has to be set. Its value is a port number what is used by both the application and WebEngineDriver to communicate with each other.</p>
<div class="pre"><pre class="cpp plain" translate="no">export QTWEBENGINE_REMOTE_DEBUGGING=12345</pre></div>
<p>By executing, the script opens the specified application and loads the Google web site.</p>
<p>WebEngineDriver can be also attached to an already running application if it was started with the remote debugging port set. <code translate="no">options.debugger_address</code> has to be set to the remote debugging address in the script:</p>
<div class="pre"><pre class="cpp prettyprint" translate="no">options<span class="operator">.</span>debugger_address <span class="operator">=</span> <span class="char">'localhost:12345'</span></pre></div>
<p>In this case, <code translate="no">options.binary_location</code> should not be set because the application is already running. The environment variable <code translate="no">QTWEBENGINE_REMOTE_DEBUGGING</code> is not used by the WebEngineDriver if <code translate="no">options.debugger_address</code> is set.</p>
<div class="admonition note">
<p><b>Note: </b>WebEngineDriver must be built with the same version of Chromium as Qt WebEngine is using.</p>
</div>
<h2 id="webgl">WebGL<a class="plink" href="#webgl" title="Direct link to this headline"></a></h2>
<p>Qt WebEngine supports WebGL for some graphics stacks setups. A user can visit the chrome://gpu page using the <a href="qtwebengine-qmlmodule.html" translate="no">QtWebEngine</a> powered application. The <i>Graphics Feature Status</i> overview states if WebGL is supported for the current platform setup. A user can also check the <a href="https://webglreport.com">WebGL Report</a>.</p>
<p>The WebGL support is enabled by default. You can disable it with the <a href="qwebenginesettings.html#WebAttribute-enum" translate="no">QWebEngineSettings::WebGLEnabled</a> setting.</p>
<p>The implementation of WebGL support is mainly provided by Chromium.</p>
<span id="webrtc-feature"></span><h2 id="webrtc">WebRTC<a class="plink" href="#webrtc" title="Direct link to this headline"></a></h2>
<p>WebRTC provides application with Real-Time Communications (RTC) capabilities via simple APIs. For more information, see <a class="obsolete" href="qml-qtwebengine-webengineview-obsolete.html#Feature-prop" translate="no">WebEngineView.Feature</a>, and QWebEnginePage::Feature.</p>
<p>This feature can be tested by setting up a webcam or microphone and then opening <code translate="no">https://test.webrtc.org/</code> in <a href="qtwebengine-webenginewidgets-simplebrowser-example.html">Simple Browser</a> or <a href="qtwebengine-webenginequick-quicknanobrowser-example.html">Nano Browser</a>.</p>
<p>The implementation of WebRTC support is provided by Chromium libraries.</p>
