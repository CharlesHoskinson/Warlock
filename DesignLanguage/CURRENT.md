## Reading the evidence

Each packet under `implementation/warlock/qa/evidence/` records observations from a named recording. Its manifest binds the exact sources and native tuple, its reports hold the checks, and its README states the scope and the obligations outside it. The descriptions below say what each packet shows about Warlock's behaviour in its recorded fixture. Independent scenario acceptance, audible speech and braille, hardware breadth and release acceptance are separate gates, and no packet closes them. The Quint models inside the packets abstract their scope and stand apart from native observation. Retained failures sit in their packets beside the passing records.

## Interaction and outcome

One Elm policy owner holds ordinary desktop policy. Typed intent crosses the bridge, and correlated native facts establish confirmed window state. Views, adapters and documentation examples hold no second authority. Keep focus, selection, the chooser's prospective window, application activity, preview freshness and action outcome distinct.

Give Pending, Refused, Cancelled and Unknown readable feedback in the outcome grammar of the [visual system](DESIGN.md). Unknown uses the read-only reconciliation path and never replays a mutation automatically. An acknowledgement proves neither displayed pixels, the actual keyboard recipient nor a completed power transition.

Reserve stable preview geometry across Loading, Live, Historical and Unavailable. Pixel arrival never moves a pressed control or reinterprets a gesture. Keep the press-time identity, publication and lease guards, cancel a mismatched release, and fix layout instead of retargeting the action ([stable targets](INTERACTION-ADDENDUM.md)).

Popup entry records pointer or keyboard origin in the single Elm policy and carries it through the stamped action relay to the projection-only renderer. Pointer dismissal yields the bar's keyboard lease before the native grab ends, and keyboard dismissal keeps its eligible bar parent. Origin is a UI return policy and grants no native authority. The [entry and return evidence](../implementation/warlock/qa/evidence/popup-entry-keyboard-return/README.md) records the taskbar journey with forward and reverse traversal, Escape and actual GTK key receipt, the keyboard-only journey across all nine surfaces with zero injected pointer events, and the modal, draft and fullscreen regressions with normal shutdown.

Preserve effective Omarchy keywords, commands, bindings and user overrides. Resolve shortcut conflicts explicitly, keep guidance dismissible and keep offline recovery reachable. The [feature checklist](../docs/warlock-roadmap/FEATURE-COMPLETION.md) tracks the binding inventory.

## Colour, depth and accessibility

Use the [layer roles](layered-windows/v1/DECISIONS.md) with Lacquer colours. The keyboard-recipient mark, active-application contour, candidate corner brackets and family brackets each carry a separate meaning. Neutral shadows express separation, and opaque owned-chrome shading groups layers. Derive their presentation from current committed native observations. Decorative effects never change scene order, eligibility or input regions.

Every cue keeps a non-colour shape or text alternative. High contrast, effects-off, reduced transparency and reduced motion preserve information and usable controls. Measure rendered labels, focus, targets and reflow, because a token value or DOM assertion alone is not a measurement. Expose complete native control semantics, use one announcement owner, and prefer keyed control identity and explicit focus changes over refocusing on unrelated updates. Search fields and buttons share one focus role.

The Lacquer tokens, contrast manifest and Hyprland values live in the [foundations](../site/design/foundations/spec.md). The [OpenSpec task list](../openspec/changes/warlock-design-language-v2/tasks.md) and the [feature checklist](../docs/warlock-roadmap/FEATURE-COMPLETION.md) track their application across the native shell, including the neutral focused-window and Hyprland values on the host path.

Settings offers **Disable soft effects** and **Reduce transparency** and saves both through the Elm preference transaction and the native private store. Drafts leave the rendered appearance unchanged, and an unconfirmed save never replays. Effects-off removes soft shadows and keeps solid focus, active and attention edges and selected contours; reduced transparency uses opaque shell backing. The [appearance evidence](../implementation/warlock/qa/evidence/layer-appearance/README.md) records a native keyboard journey that saves both flags, restarts the whole host and observes both stored flags in the bar and the popup, and browser rendering checks of all four flag pairs in Night, Dawn and High contrast at 200% text.

Keyboard focus in the taskbar and Settings paints outside the control, separately from active and pressed state. The taskbar reserves eight CSS pixels around the scaled row, the native host reserves the same band, and horizontal reveal includes the outline extent. The [outer focus evidence](../implementation/warlock/qa/evidence/outer-focus-indicators/README.md) records 102 browser checks, including 64 first and last taskbar observations across Night, Dawn, High contrast, 100% and 200% text, 320px and 800px widths, effects on and off and forced colours, and a native keyboard journey whose captures show paint of two pixels or more along all four outside edges, with a measured focus-to-background contrast of 10.22:1.

The taskbar paints its focus contour only while its WebKit document owns keyboard focus. The contour stays visible after pointer-menu use when WebKit does not match `:focus-visible`, and disappears while a popup or application owns focus. The [dense-layout evidence](../implementation/warlock/qa/evidence/dense-outer-focus/README.md) records a 150% native journey on a 480x600 output that visits all 18 configured pins, first and last menus, deliberate wheel scrolling and output resizing, with selection, the Active underline and pressed state kept separate.

## Each window and surface

Each area has a specification: the [taskbar](../site/design/taskbar/spec.md), [Applications](../site/design/launcher/spec.md), the [window switcher](../site/design/window-switcher/spec.md), [Task View](../site/design/task-view/spec.md), [previews and snap layouts](../site/design/previews-snap/spec.md), [System and menus](../site/design/system-menus/spec.md), [notifications](../site/design/notifications/spec.md), [Settings](../site/design/settings/spec.md) and [Files](../site/design/files/spec.md). Each specification defines its anatomy, states, behaviour, accessibility and renderer requirements. The surface paragraphs below restate those specifications as design guidance; the sentences that cite an evidence packet describe observed behaviour. Shell surfaces are opaque, enter and leave immediately, and never start the portal.

Record its actual implementation route and unsupported capabilities before adding specimens, and label every simulated native outcome as fixture data.

### Applications launcher

## Recovery

### Outputs

- When every real output disappears, Warlock suspends shell presentation: the compositor's internal fallback output receives no bar, popup, reserved shell band or Apps shortcut event. A returning nested output receives a fresh issued view after configure acknowledgement and restores launcher focus, the typed query and keyboard Refresh without replaying a launch or window effect. The [zero-output evidence](../implementation/warlock/qa/evidence/zero-output-return/README.md) records the return with workspace identity unchanged.
- Orphaned workspace placement includes the destination output origin and wraps negative logical coordinates without changing window size. The [placement evidence](../implementation/warlock/qa/evidence/output-placement-recovery/README.md) records the returning floating application at x=40 and y=230 with workspace 2 and its unsaved draft, activating once through the taskbar and receiving pointer and keyboard input; its vertical partial clipping is retained without a fabricated resize.
- Native workspace transfer and changed usable-area updates recover the first 32 logical pixels or fewer of an ordinary floating window inside the area left after shell reservations and floating gaps. Size, workspace and already reachable placement stay unchanged, and an unchanged-area recalculation leaves deliberate manual placement alone. The [usable-area evidence](../implementation/warlock/qa/evidence/reachable-output-area/README.md) records an application reachable at (-360,-32) on a 400×200 output with its 108×440 size, and the recovery keeps a reachable input region rather than fitting an oversized client.
- The [minimized recovery evidence](../implementation/warlock/qa/evidence/minimized-output-area/README.md) records an application minimized before the output change staying minimized through reconciliation and restoring once at (-360,-32); the packet claims no new production behaviour.
- Pinning a floating window keeps it visible across workspaces, and that state survives usable-area recovery. The [pinned usable-area evidence](../implementation/warlock/qa/evidence/pinned-output-area/README.md) records a pinned application recovered at (-360,-32) without unpinning or changing its size, workspace or draft.
- A pinned floating window follows its preserved workspace when its output retires, while a workspace moved from a live output keeps its pin on the old output. Activation from another focus output is refused to avoid implicit membership transfer. The [pinned retirement evidence](../implementation/warlock/qa/evidence/pinned-output-retirement/README.md) records pinned applications keeping workspace, size, pin state and draft through output removal, replacement, all-output disappearance and return.
- A shortcut reply carries its press-time native output generation, and Elm consumes a delayed reply without moving focus or opening a popup unless the generation matches current reconciled observations. The [delayed shortcut evidence](../implementation/warlock/qa/evidence/shortcut-generation-recovery/README.md) records an old reply delivered after a fresh view returns at identical 800×600 bounds producing visible output-unavailable feedback without relocation or replay, and the next physical shortcut opening the launcher normally.

### Outside the failed host

[Offline component recovery](../implementation/warlock/RECOVERY.md) runs from a terminal outside Elm and independently of onboarding. A recovery profile keeps one validated copy of pins, appearance, motion and explicit shortcut choices, and rollback publishes the whole route and state selection with one atomic rename. A running managed host holds the profile lock, so a competing launch refuses. An `Unknown` publication outcome is reconciled through status rather than repeated. The [offline recovery evidence](../implementation/warlock/qa/evidence/offline-recovery/README.md) records a native drill in which the standalone command selects a different retained Warlock build after the host exits, that build reads the four prior preference files, and keyboard dismissal returns to the application recipient with application identities intact.

## Contributing

The [Warlock contributor plugin](../plugins/warlock-contributor/README.md) supports Claude Code, Codex and Grok through one shared offline checker and skill. It scaffolds scenario work, protects source ownership and records bounded evidence. The [design contribution guide](CONTRIBUTING.md) explains its use for product design changes and for catalog and documentation work. Keep frozen catalogs, source manifests, consensus packets and failed evidence unchanged. Add current guidance or a fresh specimen when behaviour changes, link the real implementation route, and keep proposed, implemented and observed claims separate.

## Release artifacts

[The release builder](../implementation/warlock/RELEASE.md) assembles a local archive containing the Elm views and adapters, the native host and the exact core, plugin and Aquamarine tuple. Its embedded manifest records payload hashes, and the reviewed input lock covers sources, compiler and packages, tools and native dependencies. A changed source or artifact selection refuses the build. Build observations leave browser specimens and component evidence at their recorded scope.

[The offline reproducibility evidence](../implementation/warlock/qa/evidence/offline-reproducibility/README.md) records the fixed recipe running twice in separate Bubblewrap network, mount, PID, IPC and UTS namespaces against a read-only locked snapshot. All 56 payload file hashes and both archive hashes agree, and altered files, altered archives and a same-content loader alias each block release. The packet presents this as owner-observed partial evidence for its delivery scenario.
